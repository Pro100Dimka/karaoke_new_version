Технический отчёт: границы слов и букв караоке
Дата проверки: 31 октября 2026 года.

Статус: частично исправлено. Подтверждённые ошибки исправлены и покрыты регрессиями; остаётся воспроизводимая ошибка выравнивания слова «один», полные проверки проекта не проходят. Готовность к выпуску и выполнение всех критериев задания не подтверждены.

1. Проблема и ожидаемый результат

Правильно распознанное слово могло получить короткий интервал, а полезное совместное уточнение соседних слов терялось при применении результата. Отдельно обнаружено, что правильное окончание слова ещё не гарантирует правильной подсветки букв: финальная согласная могла оставаться в начале протяжной гласной. Требуемое поведение — следовать подтверждённым акустическим границам, сохранять быстрые слова и тишину. Общего увеличения длительностей, замедления анимации и новых моделей не добавлено.

2. Фактический путь данных

Вход обработки: python/backend/processing/start_processing.py, StartProcessing._start_job → _run → _process_with_clip. Далее PipelineOrchestrator.run в processing/orchestrator.py вызывает BuildProcessingDocument.run в processing/document_pipeline.py. Его _align передаёт выделенный вокал, текст, язык, опорные времена и инструментальную дорожку в CommandAiProvider.align из infrastructure/command_ai_provider.py; worker выполняет ai_worker/speech.py::align.

В worker используются независимое распознавание, сохранённые CTC-вероятности и опорные окна. Существенная последовательность: align_words → align_guided → with_word_guidance → with_voice_onsets → with_sung_ends → ordered → обнаружение подозрительных интервалов → локальное повторное уточнение. Теперь после него отдельно проверяются поддержанные акустикой времена финальных согласных через with_sung_letters.

Ответ worker разбирается CommandAiProvider._word в WordTiming. Затем BuildProcessingDocument._construct вызывает processing/algorithms.py::construct_document и _word_with_notes; ProjectPublisher.publish_generated и lyrics/codec.py::encode_document сохраняют lyricsSync.json. Его времена слов и букв получает frontend/src/features/karaoke/karaokeLyrics.ts, включая letterProgress и currentLineIndex. Производственный код нот и фронтенда не менялся.

Полные промежуточные состояния сохранены в cached-pipeline-before.json и cached-pipeline-after.json. Поэтому изменения оценивались до и после каждого существенного этапа, а не только по окончательному JSON.

3. Подтверждённые причины

Первая доказанная ошибка применения результата находится в speech.align. При повторной проверке исправленные слова сохранялись только для первоначально отмеченных индексов. Правильное новое начало соседнего слова заменялось старым; последующий ordered снова обрезал предыдущее слово. Дополнительное условие требовало уменьшения набора предупреждений: акустически улучшенный интервал мог быть отвергнут, если предупреждение о скорости оставалось.

В recognition.rate_review_indices использовались преимущественно письменные признаки из reporting.rate_reviews. Короткие «дом»/«дім» и «привет»/«привіт» могли не попадать на проверку, хотя независимое распознавание и продолжающийся вокал противоречили их окончаниям. Теперь учитываются активный вокал в пропущенной части независимого интервала и конфликты соседних границ. Протяжённость букв сама по себе не устанавливает минимальную длительность слова.

ctc.ordered действительно мог уничтожить подтверждённое фонетическое ядро обрезанием по раннему соседу. Теперь значимое обрезание сохраняет BoundaryConflict; конфликт не исчезает при повторной нормализации. Это диагностический сигнал для совместной проверки, а не разрешение оставлять пересечения.

В with_voice_onsets и with_sung_ends обнаружен навязанный минимум 50 мс, растягивавший реально короткие 30-мс слова. Он удалён для уточнения достоверных интервалов. Существующее акустическое определение продолжения и тишины сохранено.

В CTC слишком строгая предварительная проверка вместимости окна отклоняла допустимые быстрые пути. _align_window сразу возвращал математическое распределение _evenly. Теперь сначала выполняется ограниченная попытка в расширенном окне между существующими опорами. При невозможности выравнивания остаётся стабильный приблизительный результат с нулевой уверенностью и ApproximateAlignment; он не принимается за сильное доказательство при повторном уточнении.

Наконец, бесплатный завершающий wildcard в _transcript_path способен выбрать слабую раннюю согласную вместо настоящей поздней. Глобальное изменение wildcard ухудшало существующие реальные сценарии и было отвергнуто. Добавлена узкая повторная проверка последней согласной внутри независимо подтверждённого протяжного слова. Она требует непрерывной вокальной активности, подходящей опоры и улучшения фонетического соответствия, сохраняя начало, конец и подтверждённый префикс.

4. Что изменено

Пять производственных файлов: ai_worker/ctc.py — диагностика конфликтов, восстановление окна, быстрые интервалы и согласные; ai_worker/word_guidance.py — совместное локальное уточнение и проверка качества; ai_worker/recognition.py — акустические основания повторной проверки и диагностика; ai_worker/speech.py — применение согласованного результата; processing/reporting.py — сохранение причин проверки в отчёте.

Совместный кандидат сравнивается по CTC, независимым временам и подтверждённым входам вокала. Одного уменьшения предупреждений недостаточно. Защищены уверенные соседние начала и окончания; изменение одного входа вокала не переносит все дальние слова вслед за новой оценкой задержки. Неразрешённая подозрительность сохраняется как TimingReviewRequired.

Тестовые файлы: python/tests/test_word_timing_review.py, test_ctc_window_recovery.py, test_ctc_sustained_tail.py, test_sung_boundary_regressions.py, test_refine_words.py, test_letter_alignment.py; frontend/src/features/karaoke/karaokeLyrics.test.ts. В существующих mocks исправлены устаревшие сигнатуры без ослабления проверяемых утверждений. Обновлён генерируемый kaggle/ad_voice_p100.ipynb для доставки того же worker.

Общий diff: 13 файлов, 1220 добавлений и 69 удалений; пять производственных, семь тестовых, один notebook. Хеши 39 исходных медиафайлов и сохранённых тестовых данных не изменились. Аудиофайлы не растягивались и не сдвигались.

5. Измеренные примеры до и после

Источник: synthetic-boundaries-before.json и synthetic-boundaries-after.json. Все времена в секундах; «до/после» означает запуск прежней и изменённой реализации на одинаковом сценарии.

Сценарий                                      До                         После
«дорога», применение совместного кандидата     start=1.00, end=1.10        start=1.00, end=2.00
Её сосед «домой»                              start=1.10, end=2.50        start=2.00, end=2.50
Быстрые «и» и «і»                             start=1.00, end=1.05        start=1.00, end=1.03
«дом» и «дім», целое слово                     start=0.20, end=1.22        start=0.20, end=1.22
Их финальная «м», начало буквы                 0.28                       1.20

Первые две строки — интеграционная проверка применения заранее заданного совместного кандидата; это не измерение точности реального ASR. Последние две показывают исправление букв внутри уже правильного слова. Отдельный синтетический локальный CTC-сценарий «дом/там» успешно восстанавливал пару и до, и после изменения; его нельзя выдавать за новое улучшение.

В отдельном эксперименте с реальными сохранёнными CTC-данными chorus-entry.npz окно украинского «голос» намеренно сужено. Прежде: 9.70–9.75, уверенность 0; теперь: 9.70–10.14, уверенность 0.419. Это восстановление контролируемо повреждённого окна, а не найденное улучшение нетронутой песни. Источник: ctc-window-recovery-evidence.json.

6. Обязательные регрессии

1) Сжатие секундного слова до 0.1 с: совместное применение границ и отдельный синтетический CTC-путь.
2) Раннее следующее слово: проверка пары, сохранение конфликта, отсутствие пересечения и обратного порядка.
3) Длинная гласная без паузы: поздняя согласная восстанавливается при поддержанном непрерывном вокале.
4) Слитные слова: совместный CTC-фрагмент не требует обязательной тишины между ними.
5) Настоящие быстрые слова: 30- и 60-мс примеры сохраняются; совпадающий независимый интервал не вызывает произвольного растяжения.
6) Тишина: расширенный ASR-интервал без вокала не считается пропущенным исполнением, слово не заполняет паузу.
7) Эхо и инструментальные остатки: сохранены существующие акустические проверки; отрицательные примеры запрещают перенос согласной на позднее эхо или неподтверждённый хвост.
8) Повторы: одинаковые слова с удержаниями 1.0 и 1.65 с остаются различными; проверены существующие сценарии повторных фраз.
9) Тихие окончания: синтетический хвост с амплитудой в десять раз ниже сохраняется до 2.0 с и останавливается перед эхом с 2.45 с.
10) Ноты: исправление границы восстанавливает протяжную ноту, сохраняя MIDI, общий мелодический контур и времена кадров последующего анализа. Проверен round-trip документа через codec.

Есть русские и украинские варианты. Фронтенд-тесты проверяют интерполяцию протяжной буквы и удержание строки при правильном end последнего слова. Эти проверки покрывают перечисленные ситуации, но не гарантируют точность на любой записи.

7. Результаты и воспроизведение

Backend: в сопоставимом окружении исходная версия — 1120 passed, 84 failed, 6 skipped; исправленная — 1197 passed, 64 failed, 6 skipped. Во время обоих прогонов исходники оставались неизменными (SHA256). Все 57 добавленных backend-кейсов и 4 frontend-кейса проходят. В существующем test_letter_alignment.py проходят 149 из 151 проверок; две оставшиеся описаны ниже. Compile, bootstrap и Ruff lint прошли. Ruff format: 25 уже существующих файлов требуют форматирования. Mypy: одинаковые до/после 27 ошибок в 8 неизменённых файлах. Архитектурный gate содержит 60 диагностик до и после, при этом некоторые существующие превышения размеров выросли. Полные журналы и exit-коды: compatible-baseline/ и compatible-final/. Все текущие падающие node ID воспроизведены на исходном коде хотя бы в одном сохранённом прогоне; состав ошибок фоновых задач между запусками менялся. Это не даёт основания считать все исчезнувшие падения исправленными этим patch. Отдельный повтор library_roundtrip показал одинаковый HTTP 409 и KeyError jobId на обеих версиях до экспорта/импорта. См. failure-comparison-compatible.json.
Frontend: typecheck и архитектура прошли. Vitest: 929 passed, 2 failed; 152 из 153 файлов прошли. Node: 101 passed, 1 failed, 4 skipped. Ошибки связаны с существующими Windows-ожиданиями taskkill в ServiceProcess и cmd.exe в release-script; соответствующие исходники, тесты, package и lock побайтово совпадают с исходным архивом. Логи: frontend-compatible-*.json/.log.

Полные прогоны не зелёные. Помимо известных ошибок архитектуры и несвязанных подсистем, остаются две релевантные проверки: «один» в uncertain начинается в 9.94 вместо ожидаемого <9.5; тест CUDA-преобразования embeddings получает float16 вместо ожидаемого float32. Второй воспроизводится с mock переноса на GPU и не объясняется отсутствием CUDA. Оба существовали до изменений. Для uncertain остаются противоречивые слабые CTC/ASR-опоры; конкретная первопричина окончательно не установлена, неподтверждённое смещение не применялось. Обе первоначально выглядевшие новыми recording-ошибки отдельно воспроизвелись на исходной версии.

Архитектурные лимиты backend уже нарушались до патча, некоторые счётчики выросли; этот gate также нельзя считать пройденным.

8. Реальные фрагменты, скорость и ограничения

Три неизменённых реальных cached-сценария fast, native_fast и reply сохранили все времена слов и букв. В двух добавилась диагностика. Это подтверждает сохранение существующих результатов, но не улучшение их акустической точности.

Фрагмент (длительность)                 До, мс         После, мс       Добавлено, мс
fast (11 с)                                62.958         113.362         +50.404
native_fast (10 с)                         58.390          60.178          +1.789
reply (40 с)                              226.309         415.279        +188.970

Методика: последовательные парные CPU-запуски, один поток, пять прогретых повторов, одинаковые входные данные. Измеряется локальное выравнивание и обработка сохранённых результатов; новый ASR/MMS inference и подготовка VAD не входят. Дополнительные проверки имеют измеримую стоимость. Отсутствие существенного замедления полной обработки песни не доказано.

Полные песни с новым запуском всех моделей не проверялись. Нет ручной фонемной разметки всего набора; сложная реверберация, дыхание и слитный вокал могут оставаться неоднозначными. Обязательный живой Windows/Electron gate из AGENTS.md не выполнен. По этим причинам итог остаётся «частично исправлено», несмотря на подтверждённые исправления отдельных механизмов.

9. Окружение, применение и состав доказательств

Проверено на Linux, Python 3.12.14, Torch/Torchaudio 2.11.0+cpu, Node 24.22.1. Установленные прямые зависимости Python соответствуют ограничениям pyproject.toml; их точные версии записаны в compatible-environment.json. Это не проверка на Windows/CUDA. Полная обработка с загрузкой ASR/MMS-весов и прослушивание всех песен не выполнялись. Для завершения проверки uncertain нужен соответствующий исходный фрагмент вокала с текстом и проверенными опорами; существующая fixture этой разновидности содержит CTC/ASR, но не волну.

Готовые пользовательские lyricsSync.json автоматически не переписывались. Исправления действуют при новом выравнивании или штатном пересчёте текста существующего проекта: этот путь вызывает обновлённый worker, а сохранённые ASR/CTC могут использоваться повторно. Исходные дорожки сохраняются. Kaggle notebook пересобран локально с тем же worker; публикация/развёртывание не выполнялись.

В каталоге verification/karaoke-word-sync внутри архива находятся этот отчёт, patch, манифест 13 изменений, журналы полных и целевых проверок, JSON промежуточных состояний и воспроизводимые скрипты. patch проверен командой git apply --check на исходной копии; git diff --check пройден.

Воспроизведение сохранённых реальных данных из корня распакованного проекта:
python verification/karaoke-word-sync/cached_pipeline_evidence.py python verification/karaoke-word-sync/replayed.json --iterations 5

Воспроизведение синтетических чисел:
python verification/karaoke-word-sync/synthetic_boundary_evidence.py python python/tests verification/karaoke-word-sync/synthetic-replayed.json

Для сравнения «до» первый аргумент заменяется на python-каталог исходной распаковки; для synthetic_boundary_evidence.py второй аргумент должен оставаться каталогом новых тестов. Эти скрипты не загружают ASR/MMS-модели; маски активности для трёх реальных фрагментов приложены в acoustic_cache.
