**## II.0. Владение и transport contract**

**\*\*Показать:\*\*** существующий realtime Mixer принимает подготовленный тестовый

media source через AudioService; \`MediaContext\` и playback state не подменяют

\`SessionState\`. Команды несут явный context. Stale PCM после stop/seek/reload

не доходит до выхода.

**\*\*Приёмка:\*\*** детерминированные state/position/generation tests; ограниченный

control IPC без PCM; однозначная таблица разрешённых сочетаний источников;

никакого второго output path. Snapshot позиции опирается на render timeline,

а частота обновлений UI не определяет аудиовремя.

**## II.1. Песня: загрузка и базовый transport**

**\*\*Показать:\*\*** \`LoadSong → Ready → Play/Pause/Resume/Seek/Stop/Finished\` для

готового audio resource, с авторитетной позицией в кадрах, отдельным MusicGain

и заранее заполненным bounded decode buffer. Создание песенных файлов и

библиотека остаются за пределами AudioService.

**\*\*Приёмка:\*\*** decoder worker не блокирует RT; underrun даёт определённый output

и diagnostics; seek/stop не воспроизводят старые кадры; EOF имеет точную

позицию и событие. Измеряются load-to-ready, play-to-first-frame, latency,

CPU, память и влияние на monitoring.

**## II.2. Rate, transpose и reference vocal**

**\*\*Показать:\*\*** runtime rate, transpose и независимые gain/mute/routing двух

дорожек работают на одной playback timeline без повторного открытия output.

**\*\*Приёмка:\*\*** корректное отображение source/render position при смене rate,

синхронный seek/stop дорожек, тесты граничных значений и latency processing

в diagnostics. Заявлять поддержку конкретных rate/transpose можно только

после проверки качества и бюджета CPU на поддерживаемых конфигурациях.

**## II.3. Recording lifecycle**

**\*\*Показать:\*\*** существующая запись получает prepare/start/pause/resume/stop/

finalize, RecordingResult и связь recording frame с session/playback frame.

Запись работает без monitoring и без песни.

**\*\*Приёмка:\*\*** точная длительность, паузы и gaps в metadata, отсутствие тихой

потери PCM; slow/full disk и ошибка writer не блокируют monitoring или

playback. Старые тесты recording сохраняются как contract tests.

**## II.4. Live signal и device tests**

**\*\*Показать:\*\*** peak/RMS, presence, clipping и при необходимости лёгкий noise

floor из уже открытого входа; проверка выбранного входа и короткий test signal

через обычный output backend без Karaoke session.

**\*\*Приёмка:\*\*** метрики bounded и воспроизводимы, не требуют второго открытия

микрофона, не превращаются в offline/AI scoring; тестовый звук имеет

ограниченные уровень и длительность. При наличии существующего live pitch

публикуется его snapshot, новый алгоритм без требования не добавляется.

**## II.5. Preview редактора и записи**

**\*\*Показать:\*\*** редактор и History используют существующие decoder, Mixer и

Render: load/play/pause/seek/stop, loop с точными границами, позиция

playhead и ограниченный reference tone.

**\*\*Приёмка:\*\*** loop и seek не выпускают stale PCM; preview и Karaoke/Radio

подчиняются правилам media context; отдельного аудиодвижка нет.

**## II.6. Radio**

**\*\*Показать:\*\*** network/decoder worker подаёт radio PCM в bounded buffer и

существующий Mixer. Karaoke имеет явный приоритет над Radio.

**\*\*Приёмка:\*\*** network stall не останавливает RT, публикует buffering и

ограниченную тишину; отказ радио не ломает AudioSession. Тесты порядка

команд и разрешённых сочетаний источников обязательны.

**## II.7. Remote media lifecycle**

**\*\*Показать:\*\*** join/leave media session, отдельные source/gain/mute/level для

участников и diagnostics поверх существующего send/receive пути. Room business

logic остаётся вне AudioService.

**\*\*Приёмка:\*\*** reconnect не выпускает накопленный старый PCM burst; отказ

одного decoder не ломает других; сеть не увеличивает local monitoring latency.

Сохраняются contract и baseline основного network этапа.

**## II.8. Настройки, диагностика и ошибки**

**\*\*Показать:\*\*** live gains/mute применяются без restart; структурные изменения

используют существующий reconfiguration lifecycle. Снимок settings и

diagnostics показывает requested/runtime, состояния источников, буферы,

задержки и причины отказов.

**\*\*Приёмка:\*\*** поколение защищает все асинхронные decoder/network/recording

операции; failure одного media source изолирован; нет скрытого буфера или

неучтённого latency stage. Положения и состояния публикуются консистентно.

**## II.9. Совместный сценарий и Baseline C**

**\*\*Показать:\*\*** сочетание song, monitoring, recording, analysis, remote voices

и DSP, а также отдельные сценарии preview и radio. Дополняется Baseline C

основного плана с \`Music ON\` и параметрами \`Music Gain\`.

**\*\*Приёмка:\*\*** каждому требованию дополнения соответствует реализация,

автоматический тест/измерение/diagnostics и пользовательская проверка.

Сравниваются first-audio, steady-state latency, CPU/deadline, xruns, память,

clock/queue stability и fault recovery с Baseline A/B и основной Baseline C.

Необъяснённая регрессия блокирует завершение.

**# Владение, потоки и границы этапа 2**

**## Что существует сейчас**

\`main\` создаёт файловый лог, \`AudioService\` и \`ControlServer\` в этом порядке; уничтожение происходит в обратном порядке. \`ControlServer\` владеет handle named pipe и хранит невладеющую ссылку на лог. \`AudioService\` владеет \`SessionManager\`, backend через \`IAudioBackend\`, \`TraceBuffer\` и графом; граф владеет одним предвыделенным пулом capture/raw/render. \`SessionManager\` единолично изменяет состояние сессии, \`generationId\` и счётчик принятых callback. \`AudioService::snapshot()\` собирает состояние сервиса, сессии, backend, requested/runtime, плана, trace и последнего серьёзного отказа за один вызов; \`audio-dump\` форматирует снимок и метаданные действующего графа. Закрытый или потерянный backend не публикует активный runtime/plan. При потере устройства отдельный bounded \`FailureSnapshot\` сохраняет исходные runtime значения и план до подготовки следующего поколения.

Сейчас \`ControlServer::serve\`, \`AudioService\`, \`SessionManager\`, fake backend и граф вызываются последовательно на одном управляющем потоке. \`AudioControl.exe\` работает в отдельном процессе и обменивается только ограниченными \`ControlRequest\`/\`ControlResponse\` через named pipe. PCM через IPC не передаётся. Реального realtime, recording, analysis, network или device notification потока пока нет. Параллельный вызов методов \`AudioService\` и \`SessionManager\` не поддерживается.

**## Граница будущих callbacks**

Каждое асинхронное событие должно нести \`generationId\`. Обработка на управляющем потоке сравнит его с текущим поколением до обращения к ресурсам сессии. После \`stop\` прежнее поколение не может изменять новую сессию. Межпоточный транспорт для backend callbacks вводится вместе с реальным backend и должен быть ограниченным по ёмкости; передача через случайный mutex или файловый лог из realtime потока запрещена. Shutdown такого worker следует порядку \`stop accepting → cancel/drain → join → destroy\` до освобождения ресурсов, доступных callback.

\`TraceBuffer::push()\` принимает компактный \`TraceEvent\` с монотонным timestamp, номером кадра, поколением, типом и небольшим payload. Запись не ждёт блокировку: при занятом буфере событие теряется и увеличивается \`dropped\`. После заполнения сохраняются последние 32 события, а \`overwritten\` учитывает вытеснение старых. Вызов не выделяет память, не выполняет I/O и объявлен \`noexcept\`. \`snapshot()\` может ожидать краткую запись и поэтому разрешён только управляющему потоку. Сейчас timestamp создаётся управляющим потоком; session frame равен 0 до появления аудиовременной шкалы в этапе 5.

Будущий realtime callback не делает disk/network I/O, blocking IPC, \`Sleep\`, ожиданий mutex/потребителя, enumeration/open/close устройств, создания потоков, heap allocation/free или неограниченных операций с очередями. Он может работать только с подготовленной памятью, ограниченными очередями, atomics и неблокирующими событиями. Исключения не пересекают realtime границу: ошибка превращается в флаг/событие и управляемое решение о bypass или отказе сессии.

**## Ошибки и диагностика**

Текущие ошибки сессии классифицированы по категории и severity: \`InvalidTransition → Control/Recoverable\`, \`DeviceLost → Device/SessionFatal\`, неизвестное значение кода → \`Unknown/ServiceFatal\`. Остальные категории (\`Configuration\`, \`Backend\`, \`Realtime\`, \`Recording\`, \`Network\`, \`Dsp\`, \`Ipc\`) определяют общий словарь и получают конкретные коды по мере появления соответствующих операций. \`AudioServiceSnapshot\` содержит один набор значений для frontend/IPC; \`audio-dump\` показывает категорию, severity, размер trace, потери и последние события. При потере устройства видно последовательность событий до \`DeviceLost\`.

Текущий \`audio-dump\` получает список стадий и размер пула от действующего \`SignalGraph\`; фиксированная схема имеет нулевую алгоритмическую задержку. Тест сравнивает перечень стадий с контрактом этапа 4 и не допускает ненужных преобразований или DSP. Измеренная задержка ожидает этапа 8, отдельный \`LatencyRegistry\` — позднейшего этапа по плану. Поля clock/queue ожидают этапа 5. Отсутствующие подсистемы сейчас не показываются как активные.

**## Универсальность и переносимость аппаратной конфигурации**

\* Не считай устройство, драйвер, имя, GUID, sample rate, buffer size, channels или иное свойство тестовой машины постоянным. Получай capabilities и фактическую конфигурацию через backend во время выполнения. Не используй имя устройства вместо проверки его возможностей; workaround по модели требует документированного бага.

\* Для каждого аппаратно зависимого выбора выполняй \`requested → supported nearest/best → safe fallback\`. Если возможность отсутствует, выбирай поддерживаемый вариант или сообщай контролируемый отказ; не допускай падения и зависания.

\* Проверяй другие устройства и производителей, встроенные/USB/профессиональные и поддерживаемые Bluetooth-устройства, другие частоты и периоды, mono/stereo/multichannel, смену и отключение устройства, отсутствие сохранённого устройства. Изменение устройства требует повторного чтения runtime-параметров и пересчёта плана/буферов.

\* Фиксированные профили FakeBackend и тестов — воспроизводимые fixtures, а не значения production-оборудования. Проверка на одном ПК не заменяет capability-driven код и тесты нескольких конфигураций. Универсальное решение предпочтительнее локальной специализации, если последняя явно не запрошена.

**## Контроль зависимостей**

\* Core-слои не должны зависеть от platform-specific деталей. Допустимое направление зависимостей: \`app/session → core contracts → backend implementations\`, но не наоборот.

\* \`WASAPI\`, \`ASIO\`, Win32 и COM headers не должны проникать в \`clock\`, \`graph\`, \`mixer\`, \`recording\`, \`network\` и DSP без объективной необходимости.

\* Запрещай циклические зависимости между модулями. Если два модуля требуют друг друга, пересмотри границу ответственности вместо добавления посредника ради обхода цикла.

\* Не создавай общий \`utils\` или \`common\` как склад случайных функций. Helper должен находиться рядом с предметной областью, которой принадлежит.

**## Детерминированность и воспроизводимость**

\* Одинаковый вход, одинаковая конфигурация и одинаковые clock/network события должны давать одинаковый результат там, где алгоритм не предполагает случайности.

\* Любая случайность в fuzz, property-based и stress tests должна иметь сохраняемый seed. Любое падение должно воспроизводиться повторным запуском с тем же seed.

\* Не используй \`Sleep\` и wall-clock ожидания как способ синхронизации автоматических тестов, если можно применить fake clock, event, barrier или deterministic scheduler.

\* Все вычисления session timeline должны использовать frames и monotonic timestamps; системное календарное время не используется для audio synchronization.

**## Управление изменениями realtime path**

\* Любое изменение realtime graph требует явного before/after сравнения: active stages, buffered frames, algorithmic latency, CPU cost, allocations, xruns и measured latency.

\* Новый stage не допускается в realtime path, если его нельзя увидеть через graph introspection и latency diagnostics.

\* CI должен сравнивать фактический runtime graph с ожидаемым graph для эталонных сценариев. Неожиданный buffer, queue, conversion, resampler или DSP stage считается regression.

\* Изменение default period, queue capacity, jitter target, prefill или другого latency-sensitive значения считается изменением поведения и требует отдельного теста и baseline comparison.

**## Производительность и бюджеты**

\* Для каждого realtime этапа зафиксируй budget по времени выполнения относительно processing period. Среднее время само по себе недостаточно; отслеживай peak, deadline margin и deadline misses.

\* Не принимай оптимизацию только потому, что она уменьшила CPU. Она не должна ухудшить latency, стабильность, качество звука, читаемость или предсказуемость lifetime.

\* Не вводи SIMD, custom allocators, lock-free структуры или platform-specific optimizations без измерения, подтверждающего необходимость.

\* Любое ухудшение latency, CPU, memory, xruns, startup time или clock stability относительно baseline требует объяснения и явного решения перед merge.

**## Политика зависимостей и сторонних библиотек**

\* Новая сторонняя библиотека добавляется только при понятной необходимости. Перед добавлением оцени: realtime suitability, allocation behaviour, thread model, latency, license, maintenance, binary size и возможность замены.

\* Не позволяй сторонней библиотеке владеть главным realtime lifecycle AudioService, если это не является осознанным архитектурным решением.

\* Оборачивай внешние API на границе модуля, если их типы или semantics иначе начнут распространяться по всему проекту.

\* Версии критических audio/network/DSP зависимостей должны быть зафиксированы и обновляться отдельным контролируемым изменением с regression tests.

**## Наблюдаемость и диагностика**

\* Любая критичная подсистема должна отвечать на три вопроса: \`что сейчас происходит\`, \`почему это произошло\`, \`что происходило непосредственно перед ошибкой\`.

\* \`audio-dump\` и диагностический snapshot должны формироваться из реального runtime state, а не из requested/configured значений.

\* Диагностика не должна менять поведение realtime path. Включение дополнительных counters или tracing не должно создавать blocking I/O, allocations или заметную latency.

\* При серьёзной ошибке сохраняй bounded snapshot: backend, device/driver, requested/runtime configuration, periods, endpoint buffers, padding, active graph, queues, clocks, drift, DSP latency, xruns, deadline misses и \`generationId\`.

**## Правила безопасности lifetime и shutdown**

\* После \`stop\` или смены generation никакой callback, worker или async operation старой generation не может обращаться к уничтоженным ресурсам.

\* Shutdown каждого worker должен иметь явную последовательность: \`stop accepting → cancel/drain according to policy → join → destroy\`.

\* Любой внешний driver/API вызов, который потенциально может зависнуть, должен иметь определённую стратегию timeout/failure на control plane. Realtime thread не участвует в таком ожидании.

\* Не освобождай объект, пока существует путь, по которому внешний backend/driver ещё способен вызвать callback. Lifetime backend callbacks должен быть доказуемым.

**## Definition of Done проекта**

Изменение считается действительно завершённым только если одновременно выполнено:

\* реализация минимальна и соответствует текущему scope;

\* нет новой неоправданной abstraction;

\* ownership и lifetime однозначны;

\* threading model понятна;

\* realtime contract не нарушен;

\* новые memory/buffer/queue limits bounded;

\* latency impact известен;

\* CPU impact известен;

\* failure и recovery behaviour определены;

\* diagnostics показывают новый runtime state;

\* unit/component/integration tests соответствующего уровня проходят;

\* regression test добавлен для исправленного бага;

\* baseline не ухудшился без принятого решения;

\* старый, временный и дублирующий код удалён;

\* документация изменена только там, где изменился contract или архитектурное решение.

**# Замена реализации и удаление старого кода**

\- Если новая реализация полностью заменяет старую, старая реализация должна быть удалена в том же изменении после успешного переключения всех call sites и прохождения тестов.

\- Не оставляй рядом две реализации одной и той же ответственности без явной временной migration-причины. Запрещены постоянные пары вроде \`Old/New\`, \`Legacy/Current\`, \`V1/V2\`, \`Service/Service2\`, \`Manager/NewManager\`.

\- Git уже хранит историю. Не сохраняй старый код «на всякий случай», «вдруг понадобится» или «для сравнения».

\- Перед завершением задачи обязательно найди все ссылки на заменённую реализацию: imports/includes, registrations, factories, dependency injection, tests, mocks/fakes, configuration, feature flags, IPC handlers, documentation и build files.

\- После переключения на новую реализацию удали:

  - старые классы и функции;

  - старые файлы;

  - устаревшие интерфейсы;

  - старые tests, которые проверяют больше не существующее поведение;

  - временные adapters и compatibility wrappers, если они больше не нужны;

  - unused configuration;

  - unused feature flags;

  - dead branches;

  - лишние imports/includes;

  - неиспользуемые dependencies.

\- Не создавай новую реализацию с другим именем только ради безопасного перехода, если существующий тип можно изменить напрямую без необходимости держать обе версии.

\- Если временно нужны обе реализации, это считается migration state и должно быть явно оформлено:

  - причина;

  - какая реализация является основной;

  - условие удаления старой;

  - тест переключения;

  - срок или этап удаления.

  После выполнения условия legacy-код удаляется немедленно.

\- Не допускай долгоживущих feature flags вида \`useNewAudioEngine\`, \`useNewMixer\`, \`enableV2\`. После стабилизации новой реализации flag и старый path удаляются.

\- Не оставляй закомментированный старый код. Удаляй его полностью.

\- Не переименовывай старую реализацию в \`Legacy...\`, если она больше не используется. Если она больше не нужна — удалить.

\- При рефакторинге предпочитай изменение существующей реализации, а не создание параллельной копии файла и постепенное накопление дубликатов.

\- После замены реализации выполни поиск по проекту по старому имени, старому namespace, старым file names и старым API. Ожидаемый результат — отсутствие runtime-ссылок, кроме явно допустимой migration/documentation истории.

\- Если новая реализация использует тот же contract, старые тесты должны быть либо сохранены как contract tests для новой реализации, либо удалены только если проверяемое поведение больше не является частью требований.

\- Не удаляй тест только потому, что он мешает новой реализации. Сначала определи: изменилось требование или появилась regression. Если требование осталось, новая реализация обязана пройти тест.

\- Build должен падать на неиспользуемом или недостижимом коде там, где toolchain позволяет это обнаружить через warnings/static analysis.

**## Обязательная проверка перед завершением изменения**

Перед тем как считать замену реализации завершённой, агент обязан проверить:

\`\`\`text

1\. Все call sites используют новую реализацию

2\. Старая реализация больше нигде не вызывается

3\. Старые файлы удалены

4\. Старые tests/mocks/adapters пересмотрены

5\. Старые feature flags удалены или имеют явный migration plan

6\. Нет duplicate responsibility

7\. Нет dead code

8\. Нет unused include/import/dependency

9\. Все tests проходят

10\. Static analysis/build не показывает следы старого path

\`\`\`

**## Главный принцип**

\`\`\`text

НОВАЯ РЕАЛИЗАЦИЯ

↓

ПЕРЕКЛЮЧИТЬ ВСЕХ ПОТРЕБИТЕЛЕЙ

↓

ПРОГНАТЬ ТЕСТЫ

↓

УДАЛИТЬ СТАРУЮ РЕАЛИЗАЦИЮ

↓

УДАЛИТЬ ВРЕМЕННЫЕ МОСТЫ

↓

ПРОВЕРИТЬ ПОИСКОМ ПО ПРОЕКТУ

↓

ТОЛЬКО ПОТОМ СЧИТАТЬ ЗАДАЧУ ЗАВЕРШЁННОЙ

\`\`\`

Исключение только одно: временная совместимость действительно нужна и явно описана как migration. Во всех остальных случаях в проекте должна оставаться одна актуальная реализация одной ответственности.
