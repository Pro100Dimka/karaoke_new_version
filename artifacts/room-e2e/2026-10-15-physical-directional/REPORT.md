## Результат: отставание пришедшего голоса от местного минуса (конечный выход принимающего ПК)

Дедлайн комнаты сервер выбирает при каждом старте песни; внутри песни он постоянен (проверено
в каждом прогоне по `RoomPlayoutDelayFrames`). Поэтому рядом указан дедлайн и
«отставание − дедлайн» — физический путь передающего ПК, который метки не покрывают.

| Направление | Прогон | Дедлайн | Начало / середина / конец | Медиана по песне (10-с окна) | − дедлайн |
|---|---|---|---|---|---|
| host → laptop | attempt1 (с 42 с песни) | 87.5 мс | — / 92.5 / 92.0 | 92.0 (88.6–92.8) | ≈ 4.5 |
| host → laptop | attempt3 | 122.5 мс | 124.8 / 130.2 / 128.1 | 127.5 (124.7–130.1) | ≈ 5 |
| host → laptop | финальный | 60 мс | 61.9 / 60.2 / 64.6 | 61.9 (54.2–66.3) | ≈ 2 |
| laptop → host | low-latency mic **ON** | 90 мс | 113.9 / 109.7 / 113.6 | **110.2** (105.8–116.2) | ≈ 20 |
| laptop → host | контроль, **OFF** | 135 мс | 133.4 / 132.0 / 133.6 | **132.8** (123.7–135.9) | ≈ −2 |

attempt2 (запись началась на 94-й секунде песни) не используется.

**Главный вопрос.** laptop → host с «Минимальной задержкой микрофона»: 110 мс против 133 мс
без неё, в одной сессии и в одной комнате — **−23 мс**. Это совпадает с локальным замером
(−23…24 мс). При выключенной галочке хост измерил более поздний приход голоса ноутбука
(`RoomArrivalRequirementFrames` хоста 4320–4536 против 2448–2496), и сервер поднял дедлайн
до 135 мс. Поэтому выигрыш галочки проявляется в комнате через дедлайн.

**Асимметрия.** Путь передающего ПК: хост (ASIO) ≈ 2–5 мс, ноутбук (Windows + Exclusive-вход)
≈ 20 мс. Отставание laptop → host больше на ~15–18 мс при одинаковом дедлайне.

**Drift.** Нет ни в одном прогоне: «конец − начало» от −0.6 до +3.3 мс, наклон по песне
не выше ±4 мс/мин. Внутри песни отставание гуляет ступеньками в пределах 5–12 мс
(финальный host → laptop: 54 → 66 мс), без монотонного роста.

**Критерий плана.** По порогу плана (нормированная корреляция ≥ 0.2) во всех окнах голос
«не найден»: акустический путь динамик → комната → микрофон даёт корреляцию 0.08–0.20.
Значения выше получены по вторичному критерию: пик в 30–85 раз выше шумового уровня
корреляции, одна и та же задержка в соседних окнах, полярность не учитывается (микрофон
переворачивал фазу). Окна с совпадением около 0 мс — это остатки вокала в самом минусе
(совпадают с местным минусом), они исключены и помечены `localBleed`.

## Не выполнено

- **Monitoring ON** не проверялся. Этот стенд специально построен на динамиках (передающий
  ПК играет вокал из динамика в свой микрофон), а проверка мониторинга требует наушников
  без акустической петли. Включённый мониторинг здесь дал бы обратную связь.
- Окно «начало» есть не во всех прогонах host → laptop (attempt1).

## Наблюдения вне рамок теста

- После окончания комнатной песни хост сам заново проигрывал её с начала, пока ноутбук стоял
  (`PlaybackState` 3 на хосте, 0 на ноутбуке, позиция с 0 до конца песни).
- Мои диагностические записи `tap=master` через AudioControl ломали обычное сохранение записи
  в приложении: окно «Идёт запись» не закрывалось, пока я не перезагрузил страницу. Это эффект
  тестовой процедуры (параллельная запись поверх пользовательской), а не обычного сценария.

## Крупнейший оставшийся источник задержки

Дедлайн комнаты: 60–135 мс. Он менялся от старта к старту даже при одной конфигурации
(60 / 87.5 / 122.5 мс в host → laptop), хотя измеренные требования прихода и возврата были
26–52 мс. Локальный путь передающего ПК — 2–5 мс у хоста и ≈ 20 мс у ноутбука. По условиям
задачи дедлайн и серверная политика не менялись.
