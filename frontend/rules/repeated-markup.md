# Повторяющаяся разметка: `map` и компоненты

Статус: **LOCKED**.

## Базовый выбор

```text
ПОВТОРЯЮТСЯ ТОЛЬКО ДАННЫЕ
→ MAP

ПОВТОРЯЕТСЯ САМОСТОЯТЕЛЬНЫЙ UI-КОНЦЕПТ
→ COMPONENT

ПОВТОРЯЕТСЯ UI-КОНЦЕПТ СПИСКОМ
→ MAP + COMPONENT

ПОВТОРЯЕТСЯ ПОВЕДЕНИЕ
→ HOOK / FUNCTION

ПОВТОРЯЕТСЯ DOMAIN-ПРАВИЛО
→ ОДНА CANONICAL LOGIC
```

## Правила

1. Если JSX повторяется и отличается только данными (`label`, `icon`, `value`, `handler`, `status`) — описывать данные один раз и выводить через `map`.
2. `map` применять только к одинаковой структуре; сильно разное поведение оставлять явным.
3. Не строить giant config-driven renderer ради разных по смыслу блоков.
4. Конечные статусы выводить через один typed mapping.
5. Одинаковую status presentation semantics не дублировать в нескольких компонентах.
6. Повторяющиеся toolbar/menu/navigation/tab/select/radio items описывать typed data и рендерить через `map`.
7. Повторяющиеся одинаковые form fields можно описывать data map, но сложную форму нельзя превращать в JSON engine.
8. Если повторяется самостоятельный смысловой блок (`SongCard`, `Participant`, `SettingRow`, `StatCard`, `EmptyState`) — выносить в компонент.
9. Не создавать компонент только потому, что несколько строк визуально похожи и не имеют самостоятельного смысла.
10. Два повторения ещё не обязаны становиться abstraction; три и более одинаковых data-driven блока — сильный кандидат.
11. Повторяющийся `label/value` layout должен иметь один reusable concept вроде `InfoRow`, когда semantics действительно одинакова.
12. Shared confirmation/dialog pattern допустим только при одинаковой semantics; не делать universal dialog с десятками props.
13. Callback внутри `.map()` должен оставаться коротким и читаемым. Большой item renderer → отдельный component.
14. Логику item не вычислять внутри `.map()`, если её можно инкапсулировать в item component.
15. Не создавать лишние Container/View слои (`SongCardContainer` + `SongCardView`) без необходимости.
16. Map config должен быть typed.
17. Для закрытых списков использовать `as const`.
18. Для полного mapping union использовать `satisfies Record<Union, Config>`.
19. Не использовать `Object.entries` с потерей типов без необходимости.
20. Статический data map хранить на module level; динамический — внутри component, если он зависит от props/state.
21. Не выносить dynamic config наружу через фабрики только ради псевдо-оптимизации.
22. Не сокращать код так, чтобы исчезал смысл. Цель — меньше duplication и мест для ошибок, а не минимальное число строк.
23. Одинаковый layout + разные данные → reusable component/map только при одинаковой semantics.
24. Данные отдельно, UI отдельно. JSX в config допустим только для простых action/icon mappings, когда это действительно упрощает код.
25. Списки одинаковых UI concepts должны выглядеть как короткий `items.map(item => <ItemComponent ... />)`.
26. Не писать один и тот же `ParticipantCard`/`SongCard` вручную несколько раз.
27. Не делать giant `.map()` вместо item component.
28. Повторяющееся domain-правило имеет одну canonical реализацию/таблицу.
29. Не использовать один инструмент для всех видов повторения: `map`, component, hook/function и canonical domain logic решают разные задачи.
30. JSX должен оставаться явным там, где блок уникален.

## Главное правило

```text
ЕСЛИ БЛОКИ ОДИНАКОВЫЕ
И ОТЛИЧАЮТСЯ ТОЛЬКО ДАННЫМИ
→ ОПИСАТЬ ДАННЫЕ ОДИН РАЗ
И ВЫВЕСТИ ЧЕРЕЗ MAP

ЕСЛИ ОДИНАКОВЫЙ БЛОК
ИМЕЕТ САМОСТОЯТЕЛЬНЫЙ СМЫСЛ
→ ВЫНЕСТИ ЕГО В COMPONENT

ЕСЛИ ЭТО СПИСОК ТАКИХ БЛОКОВ
→ MAP + COMPONENT
```
