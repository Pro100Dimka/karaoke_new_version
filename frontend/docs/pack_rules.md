# Правило выбора внешней библиотеки перед собственной реализацией

Перед реализацией новой технической функции разработчик обязан сначала проверить, существует ли уже подходящее готовое решение.

Порядок:

```text
1. Точно определить задачу и требования.

2. Проверить:
   - стандартную библиотеку языка;
   - возможности уже установленных зависимостей;
   - официальные библиотеки используемого framework/runtime;
   - существующие внешние библиотеки.

3. Найти несколько релевантных решений, если они существуют.

4. Сравнить готовое решение с собственной реализацией.

5. Только после сравнения принять решение:
   - использовать существующую библиотеку;
   - расширить уже используемую библиотеку;
   - написать маленький собственный adapter/helper;
   - реализовать функциональность самостоятельно.
```

---

## Нельзя сразу писать свою реализацию

Запрещён подход:

```text
увидел задачу
↓
сразу написал собственный parser / cache / retry / queue / validator / component
```

без проверки уже существующих решений.

---

## Сначала проверить стандартные возможности

Приоритет поиска:

```text
1. Возможности самого языка/runtime.
2. Уже подключённые зависимости проекта.
3. Официальные библиотеки framework.
4. Хорошо поддерживаемые внешние библиотеки.
5. Собственная реализация.
```

Нельзя добавлять dependency, если задача уже нормально решается стандартными средствами.

---

## Проверка в интернете обязательна для нетривиальной задачи

Перед реализацией новой нетривиальной инфраструктурной возможности нужно проверить актуальные решения и документацию.

Например:

```text
state management
virtualization
forms
schema validation
retry
caching
database migration
file watching
archives
audio decoding
AI runtime
IPC
logging
testing
```

---

## Искать не одну библиотеку

Если есть выбор, проверить минимум несколько подходящих вариантов, а не брать первый результат поиска.

---

## Оценивать библиотеку не по популярности одной цифрой

Проверить:

```text
актуальность;
последний release;
поддерживаемые версии runtime/framework;
документацию;
типизацию;
размер зависимости;
transitive dependencies;
security history;
licence;
maintenance activity;
issue tracker;
breaking-change history;
API complexity;
качество тестов;
совместимость с архитектурой проекта.
```

---

## Проверить, решает ли библиотека именно нашу задачу

Не добавлять большую библиотеку, если используется только:

```text
5–20% её возможностей
```

и нужная функция реализуется безопасно и понятно маленьким локальным кодом.

---

## Сравнить стоимость зависимости и собственной реализации

Перед решением оценить:

```text
сколько кода нужно написать самостоятельно;
насколько задача сложна;
есть ли много edge cases;
есть ли security risks;
сколько тестов потребуется;
насколько сложно поддерживать собственную реализацию;
насколько библиотека усложнит проект;
как часто библиотеку придётся обновлять.
```

---

## Когда библиотека обычно лучше

Предпочитать готовую зрелую библиотеку, если задача:

```text
сложная;
стандартизированная;
имеет много edge cases;
security-sensitive;
требует поддержки форматов/протоколов;
уже качественно решена экосистемой.
```

Например не писать собственный:

```text
ZIP parser;
JWT implementation;
cryptography;
HTML sanitizer;
database engine;
complex schema validator;
virtualization engine;
```

без очень серьёзной причины.

---

## Когда своя реализация обычно лучше

Предпочитать собственный небольшой код, если задача:

```text
маленькая;
специфичная проекту;
имеет простой contract;
реализуется понятно в нескольких десятках строк;
не требует сложных edge cases;
внешняя библиотека значительно тяжелее самой задачи.
```

Пример:

```text
не подключать огромную utility library
ради одного clamp() или debounce(),
если маленький проверенный helper полностью закрывает задачу.
```

---

## Нельзя добавлять библиотеку только ради сокращения кода

Dependency должна уменьшать общую сложность проекта, а не только количество написанных строк.

---

## Нельзя писать свою библиотеку только ради полного контроля

«Будет своё» не является техническим аргументом.

---

## Нельзя выбирать библиотеку только потому, что она популярная

Она должна подходить:

```text
нашей архитектуре;
runtime;
licence;
performance;
bundle/runtime budget;
maintenance policy.
```

---

## Проверить уже установленные зависимости

Перед `npm install` / `pip install` обязательно проверить, не умеет ли это уже существующая зависимость проекта.

Запрещено иметь:

```text
две библиотеки для debounce;
две schema libraries;
две date libraries;
две state-management libraries;
```

без явной причины.

---

## Новая dependency требует justification

Для нетривиальной зависимости до добавления кратко зафиксировать:

```text
какую проблему решает;
почему стандартных средств недостаточно;
какие альтернативы рассмотрены;
почему выбрана именно она;
какие риски она добавляет.
```

---

## Проверять licence

До подключения зависимости убедиться, что licence совместима с проектом и его способом распространения.

---

## Проверять security

Для зависимости, работающей с:

```text
network;
files;
archives;
HTML;
auth;
crypto;
native code;
```

security assessment обязателен.

---

## Проверять размер зависимости

Для frontend учитывать:

```text
bundle size;
tree shaking;
loaded chunk size;
startup impact.
```

Для Python:

```text
installation size;
transitive packages;
native wheels;
startup/import cost;
memory footprint.
```

---

## Проверять native dependencies

Если библиотека требует:

```text
C/C++;
CUDA;
system DLL;
compiler;
platform-specific runtime;
```

это должно быть осознанное решение.

---

## Проверять Windows compatibility

Так как приложение desktop/Windows-oriented, библиотека должна быть проверена на целевой Windows runtime, если её работа зависит от ОС.

---

## Проверять TypeScript typing

Для frontend предпочтительна библиотека с качественными встроенными TypeScript types.

Не добавлять poorly typed dependency без сильной причины.

---

## Проверять API surface

Если для простой задачи библиотека заставляет создать:

```text
provider
registry
factory
plugin
adapter
configuration tree
```

возможно, собственное маленькое решение проще.

---

## Не оборачивать каждую библиотеку автоматически

Adapter нужен, если:

```text
это внешний архитектурный boundary;
библиотеку реально может понадобиться заменить;
API библиотеки не должен протекать по всему проекту.
```

Для маленького utility прямое использование допустимо.

---

## Внешняя библиотека не должна стать domain model

Project code не должен зависеть от специфичных типов библиотеки по всей кодовой базе, если библиотека является инфраструктурной деталью.

---

## Dependency должна иметь одного владельца по смыслу

Например:

```text
virtualization dependency
→ Library UI boundary

AI provider library
→ AI infrastructure

ZIP library
→ Packages infrastructure
```

Не импортировать её хаотично во все feature.

---

## После выбора своей реализации

Если принято решение писать самим, нужно отдельно подтвердить:

```text
почему готовые решения не подходят;
какой минимальный scope своей реализации;
какие edge cases необходимо покрыть;
какие tests обязательны.
```

---

## Своя реализация должна быть минимальной

Не начинать писать внутренний framework, если нужен один helper.

---

## Если своя реализация начинает расти

Если собственный код становится:

```text
сложным;
большим;
security-sensitive;
трудно тестируемым;
```

нужно повторно провести поиск готовых решений.

---

## Решение можно пересмотреть

Если спустя время появилась зрелая библиотека, которая значительно упрощает код, допустима замена собственной реализации.

При этом действует правило полной замены:

```text
подключить новый путь
→ перевести consumers
→ tests
→ удалить старую реализацию
→ удалить лишние dependencies
```

---

# Короткое универсальное правило

```text
BEFORE IMPLEMENTING A NON-TRIVIAL TECHNICAL FEATURE:

SEARCH
→ COMPARE
→ EVALUATE
→ DECIDE
→ IMPLEMENT
```

---
