## Караоке

### Перемотка не накапливает устаревшие позиции

Каждое движение указателя по Waveform вызывало `audioClient.seek()`.
Общая очередь выполняла диагностику, native Seek и чтение snapshot для
каждой промежуточной позиции. Даже если нижний transport умел объединять
команды, до него они доходили последовательно.

`createCoalescedAudioOperation` в `audioSession.ts` объединяет соседние
ожидающие перемотки одного владельца. Выполняющаяся операция заканчивается,
а следующая использует последнюю запрошенную позицию. Любая другая операция
в общей очереди остаётся барьером; Pause, Play, Stop и Load сохраняют порядок.
Разные функции `isCurrent` обозначают разных владельцев и не объединяются.
Ожидающие получают общий результат либо ошибку, после ошибки очередь работает
дальше. После snapshot дополнительно проверяется актуальность владельца.

Доказательство: одна уже выполняющаяся перемотка и **120 последующих позиций
дают две native Seek**, текущую и последнюю ожидающую. Новые тесты дали
7 failed / 1 passed до исправления; после него прошли **65 тестов в 6 файлах**
с потребителями управления караоке, preview редактора, telemetry и recovery.

### Расчёт оценки во время активного пения

На каждом новом pitch frame прежний расчёт снова проходил накопленные
отклонения. Кеш предыдущего прохода помогал в инструментальных паузах,
но не при поступлении новых измерений. После пяти минут пения следующие
120 кадров читали **2 095 192 старых samples**.

`NoteProgress` теперь дополнительно хранит минимальное и максимальное
отклонение. Если весь диапазон входит в прежний допуск относительно среднего,
стабильная длительность уже известна из `voiced`. Если весь диапазон лежит
с одной внешней стороны допуска, она равна нулю. Для смешанных диапазонов
сохранён точный обход samples. Независимые суммы общего score объединены
в один проход с сохранением порядка сложения каждого поля.

Допуск, частота анализа, округление и правила оценки не менялись. Внешнее
сравнение с baseline через `assert.deepStrictEqual` на **64 seeded fixtures
и 76 800 кадрах** дало точное равенство всех полей score, events, hit IDs,
live target, energy и streak. Включены seek, transpose, reset, confidence,
silence, contour, границы ±1 semitone и нечисловые входы. Прошли **54 теста
в 4 файлах** и app TypeScript.

Пять чередующихся запусков before/after; медиана медиан 120 операций
`update + noteScore` после накопления указанной истории:

| --- | ---: | ---: | ---: |

Это elapsed time указанного вычисления на тестовой машине, не FPS,
аудиозадержка или общий CPU приложения. На смешанных диапазонах остаётся
точный fallback; результат не обобщается на любой характер пения.

### Waveform до получения peaks

`SongStrip` передавал новый пустой массив на каждом изменении позиции,
пока waveform peaks отсутствовали. Это заставляло UI-kit заново строить
колонки и два SVG path. Теперь пустая коллекция сохраняет ссылку.

В тесте с настоящим UI-kit **60 обновлений позиции: 192 000 вызовов
`Number.toFixed` для координат → 0**. При появлении или исчезновении peaks
геометрия обновляется; позиция slider продолжает обновляться. Прошли
**4 теста в 2 файлах**, включая Transport.

Первоначальная гипотеза о повторном кодировании SVG masks не подтвердилась:
маски уже удерживались отдельным memo по строкам paths. Исправлен именно
повторный расчёт геометрии, а не кодирование масок.

строили все ноты, слова и секундные метки. Новый `EditorPianoRoll` рендерит
видимое время с запасом в один viewport. Полный документ остаётся источником
выделения, изменения, undo/redo и сохранения. Блочный индекс учитывает

учитывает весь исходный порядок. При независимом review обнаружено, что
`preventScroll: true` скрывал вертикальное раскрытие следующей ноты.
Исправлено обычным `focus()` с отдельной проверкой.

ResizeObserver и автопрокрутка обновляют окно; после далёкого follow-перехода
подсветка нового окна выставляется сразу. Прежняя абсолютная геометрия

## Записи

### Отзывчивая перемотка preview

`useRecordingPlayback` раньше запрашивал status и native seek для каждого
движения указателя; UI ждал ответа. Теперь позиция на экране меняется сразу,
один drain сохраняет только последнюю ожидающую цель, а пришедшая старая
telemetry не возвращает slider назад. Начатая перемотка заканчивается.

Pause/Play ждут текущий drain, первоначальная загрузка применяет последний
запрос даже при новых движениях во время native seek. Смена записи,
release/unmount и generation отменяют устаревшую работу. Одна ошибка
завершает текущую группу, возвращает последнюю подтверждённую позицию
и допускает повторную попытку новым жестом.

Доказательства: **100 запросов при удержанном status → один status и один
seek в последнюю позицию**; при уже начатом первом seek выполняются только
позиции 1 и 100, затем Pause. Проверены loading, telemetry, unmount/replace,
ошибка и retry. Новые случаи: 4 failed / 2 passed до изменения; после него
прошли **35 тестов в 4 файлах**, включая RecordingPlayer и audioPlayers.

### Общий наблюдатель видимости

`useNearView` создавал отдельный IntersectionObserver для каждой карточки.
Теперь один наблюдатель обслуживает все ещё не показанные карточки одного
document и margin. Каждый элемент активируется отдельно и снимается с
наблюдения после первого появления; последний уходящий элемент освобождает
наблюдатель. Отсутствие API сохраняет немедленное отображение player.

В regression на **500 карточек создаётся один observer вместо 500**.
Проверены разные margins, StrictMode cleanup, закрытие и устаревший callback.
Тяжёлые player сохраняют прежнее поведение near-view. Прошли **11 тестов
в 3 файлах** и app TypeScript. Поддержка нескольких targets одним observer
описана в [MDN](https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver/observe).

### Большая галерея не создаёт все тяжёлые карточки при открытии

Дополнительный probe показал, что одного объединения observers недостаточно:
до первого near-view callback галерея из 500 исполнений уже создавала
24 000 DOM-элементов, 2000 кнопок, 2500 SVG, 500 рамок и 500 disabled query
observers. Настоящих player и waveform в этот момент было ноль.

Теперь в Grid при более чем 40 исполнениях внешний `li` сначала содержит
лёгкие строки-заглушки. Содержимое `RecordingCardBody`, декоративные элементы
и `useQuery` создаются при приближении к экрану или получении фокуса.
Обычные, versions, progress и failure rows резервируют место отдельно;
текст ошибки переносится, общей фиксированной высоты карточки нет.

После первой активации body остаётся смонтированным: прокрутка сохраняет
версию, черновик переименования, позицию, громкость, паузу и активный preview.
Вход через Tab раскрывает карточку и передаёт фокус первому или последнему
доступному control в зависимости от направления. Проверка `activeElement`
защищает от позднего перехвата фокуса. Малые галереи, focused view и среда
без IntersectionObserver создают body сразу.

Одинаковый probe использует реальный Modal, UI-kit и QueryClient. IO ещё не
сообщил о видимости; при переключении List → Grid сохраняется одна уже
открытая карточка. Время — медиана трёх Linux/jsdom измерений render/commit,
без реального layout, paint, GPU и сети:

| Исполнения | DOM до → после | Card / рамки / query observers до → после | Время до → после |
| --- | ---: | ---: | ---: |
| 300 | 14 400 → 2739 | 300 → 1 | 431,83 → 78,23 мс |
| 500 | 24 000 → 4539 | 500 → 1 | 562,34 → 87,19 мс |
| 500 и 125 master versions | 25 500 → 4675 | 500 → 1 | 602,44 → 103,08 мс |

Для 30 карточек DOM и query count сохранены; наблюдаемая медиана колебалась
с 26,79 до 39,95 мс, поэтому выигрыш малого сценария не заявляется.
Суммарное CPU процесса Node не трактуется как длительность блокировки UI.

Новые assertions сначала дали **5 failed / 3 passed**. После исправления —
**30 уникальных passing tests в 6 файлах**: 11 gallery и 19 прежних consumers
(card actions/memo, player interactions, modal recovery, удаление записи).
Усиленные проверки query выполняют настоящий запрос только для активированной
`Succeeded` карточки; соседняя ждёт своей активации. Последний повтор этих
11 тестов прошёл и не прибавляется к общему числу. Независимый review проверил
lifetime, ключи player, focus, threshold 40/41, List/Grid и IO fallback.

Это исправление первоначального массового mount. Уже посещённые карточки
остаются в DOM ради сохранения состояния; полного удаления невидимых
карточек здесь нет. Реальный Electron layout и Tab scrolling требуют
живой проверки.

## Backend

### CPU admission и capabilities не запускают лишний NVIDIA probe

`without_waiting()` не ждал загрузку Torch, но на уже прогретом CUDA runtime
всё равно вызывал `nvidia-smi` ради свежей VRAM. Из-за этого CPU lease и
`/capabilities` могли ждать subprocess, который им не нужен.

Для этих двух consumers используется snapshot с
`refresh_gpu_memory=False`. Он сохраняет известные сведения о Torch и
оборудовании. Явная диагностика и CUDA admission по умолчанию по-прежнему
получают свежую VRAM; выбор устройства и вычислительные бюджеты сохранены.

Тест удерживает `nvidia-smi`, оставляя остальные зависимости доступными:
до исправления CPU/capabilities блокировались (**2 failed / 2 passed**),
после исправления прошли **34 теста** затронутых runtime/resources/scheduler
и processing consumers. Ruff lint/format и mypy с `--platform win32` прошли.

### Библиотека не перечитывает неизменённые видеоклипы целиком

Расчёт `projectHash` для Ready-песен с локальным видео включал SHA256 всего
клипа. Прежний memory LRU на 256 записей полностью терял пользу при
последовательном обходе 300 клипов: очередное открытие снова хешировало все
300 файлов. Перезапуск также терял весь memory cache.

Новый `FileHashCache` подключён только к библиотечному `GetSong`. Он использует
штатный `roots.cache / "clip-hashes"`: до 256 записей в памяти и 256 дисковых
buckets, каждый до 64 записей. Ключ учитывает путь, валидность — device,
inode, размер, mtime_ns и ctime_ns. Одновременные запросы одного клипа
объединяются; другой клип не ждёт его хеширования. После реального SHA256
повторный stat не позволяет сохранить результат, если файл менялся при чтении.

**300 неизменённых клипов: 300 повторных полных SHA256 → 0**, как при refresh,
так и после пересоздания backend query. Читаются небольшие cache records.
Первый hash нового/изменённого видео сохраняется. Import, export и validator
продолжают применять реальный hasher, формат проекта и HTTP DTO не изменены.

Read-only, повреждённый, переполненный или недоступный cache не скрывает песню:
используется реальное вычисление. Запись идёт в уникальный temporary file,
который закрывается перед atomic replace. Review воспроизвёл пересечение двух
cache instances общего root при прежнем fixed temporary filename; отдельный
regression проверяет исправление. Для disposable cache не добавляется fsync
на каждый клип: **300 лишних flush barriers → 0**. Ускорение первого открытия
на Windows/HDD из этого числа не выводится.

Окончательный gate — **30 тестов**, включая изменение и замену файлов того же
размера, изменение при хешировании, corrupt/read-only cache, concurrent reads
и writers, ограничения памяти/buckets, import/export, editor revision и songs
API. Ruff lint/format для 5 файлов и mypy для 3 production-файлов прошли.
Python architecture checker сообщает **11 прежних замечаний, новых нет**;
глобально зелёным он не объявляется.

Cache hit проверяет метаданные, а не содержимое криптографически. Изменение
с восстановленным mtime и прежней file identity может остаться незамеченным.
В частности, ctime на Windows исторически обозначает creation time, что
указано в [Python os.stat documentation](https://docs.python.org/3.12/library/os.html#os.stat_result).
Это ограничение metadata cache, поэтому проверка целостности проектов им
не заменяется. При заполнении bucket старые записи вытесняются; размер кеша
ограничен, бесконечная библиотека без повторного хеширования не обещается.
