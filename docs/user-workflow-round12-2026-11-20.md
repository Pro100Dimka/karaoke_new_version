## 1. Движение края ноты без изменения её длины уничтожало Redo

Пользователь меняет высоту ноты, отменяет изменение и слегка тянет край ноты. Если привязка к сетке или граница слова оставляет край на прежнем месте, содержимое документа фактически не меняется. Раньше `resizeNote` всё равно создавал новый объект документа. История считала его новым изменением и удаляла возможность повторить отменённое действие. Нота оставалась прежней, кнопка сохранения была недоступна, но Redo уже пропадал.

В `frontend/src/application/editor/editorModel.ts` после применения существующих ограничений добавлен возврат исходного документа, если начало и конец ноты не изменились. Реальное изменение границы продолжает использовать прежний путь обновления.

Два новых сценария в `frontend/src/pages/editor/EditorPage.gestures.test.tsx` используют настоящие EditorPage, PianoRoll, сессию и историю. Они воспроизводят оба ограничения, проверяют неизменность геометрии и состояния сохранения, затем повторяют отменённое изменение высоты. Дополнительно проверены существующие перенос, изменение длины, отмена жеста, Undo/Redo и непосредственные вызовы модели изменения границы.

## 2. Неудалившиеся файлы песни теряли возможность повторной очистки

При удалении песни отдельный файл может быть временно недоступен для удаления. Реальный `shutil.rmtree(..., ignore_errors=True)` подавляет такую ошибку. Раньше успешный возврат этой функции считался завершением очистки: песня уже исчезала из библиотеки, оставшиеся файлы продолжали занимать место, а запись для повторной попытки удалялась. Та же ошибка была в восстановлении незавершённого удаления при запуске программы.

В `DeleteSong._finalize` и `RecoverTransactions._song_delete` теперь проверяется, исчез ли каталог удаляемой песни после очистки. Если он остался, используется существующая обработка отложенного удаления: подтверждённое удаление из библиотеки сохраняется, запуск программы продолжается, а запись журнала остаётся до успешной очистки при последующем запуске.

Изменены только `python/backend/songs/delete_song.py` и `python/backend/recovery/recover_transactions.py`. Общая функция удаления каталогов не менялась: после просмотра её потребителей проверка добавлена именно в два владельца завершённого удаления песни. Поведение отката импорта и восстановления существующей песни сохраняется.

Новый `python/tests/test_song_delete_file_cleanup.py` оставляет реальными рекурсивное удаление, локальное хранилище, SQLite, DELETE API и восстановление при запуске. Временно запрещается только низкоуровневый `os.unlink` управляемого исходника. Проверены сохранность записи журнала и оставшихся байтов при отказе, повторный запуск с сохраняющимся отказом и успешная очистка после его снятия. Внешний исходный файл остаётся неизменным. Используется синтетический WAV длиной 0,125 секунды; обработка песни не запрашивается.

Предыдущие проверки отложенного удаления выбрасывали исключение из замены самого `rmtree`, обходя его реальное `ignore_errors`. Новые проверки закрывают именно этот пропущенный путь.

Исправление сохраняет повторную попытку для текущих и будущих удалений. Исторические остатки, для которых запись журнала уже потеряна, автоматически не сканируются и не удаляются.

## 3. После ошибки смены фото показывалось несохранённое изображение

При выборе фото в настройках настоящий FilePicker сразу показывает предварительный просмотр. Если чтение изображения или загрузка заканчивается ошибкой, сохранённый адрес фото остаётся прежним. Компонент очищает свой предварительный просмотр только при изменении этого адреса, поэтому продолжал показывать отвергнутое фото. После повторного открытия настроек пользователь снова видел старое изображение. При первом неудачном выборе вместо инициалов также оставалось несохранённое фото.

В `frontend/src/pages/library/modals/settings/appearance/index.tsx` при ошибке теперь меняется локальный ключ сброса. В `rows.tsx` этот ключ передаётся только FilePicker. Компонент освобождает временный object URL и возвращает сохранённое фото либо инициалы. Поле имени, остальные настройки и сама форма остаются на месте. Успешная загрузка использует прежнюю логику.

Публичный API и установленная реализация FilePicker просмотрены: отдельного управления предварительным просмотром или метода сброса нет. Зависимость не изменялась.

Новый `AppearancePanel.photo.test.tsx` рядом с компонентом использует настоящие AppearancePanel, AppearanceFields, FilePicker, Avatar, usePersonPhoto и уведомления. Проверены отказ декодирования, отказ загрузки, первый неудачный выбор, сообщение об ошибке, повторный выбор того же файла и обычная успешная загрузка. Сохраняются значение и тот же DOM-элемент поля имени, а также другая изменённая настройка. Декодирование и серверный API подменены; действий с настоящим аккаунтом не выполнялось.
