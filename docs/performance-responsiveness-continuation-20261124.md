Репозиторий: `karaoke_new_version`. Работа продолжена в существующей ветке
`perf/responsiveness-20261124` после `1a8042550aba45a59a5f2d54ae6fa30470940840`.
Новая рабочая ветка не создавалась; изменения с `main` не объединялись.
Первый набор исправлений описан в [основном отчёте](performance-responsiveness-20261124.md).

## 1. Автосохранение большого редакторского документа

### Причина задержки

Каждый autosave после 600 мс без нового изменения сериализовал весь документ
и записывал его в localStorage. Даже перемещение одной ноты повторно обходило
неизменившиеся contour points, vocalActivity и rhythm. Исправления drag-preview
из первого прохода сокращали частоту перерисовок, но не стоимость такой записи.

### Изменение

Черновик хранит обычные изменяемые поля и ссылки на неизменившийся анализ
сохранённой ревизии. Наследуются только те массивы, которые действительно
разделяют ссылку с базовым документом. Отличающиеся, отдельно разобранные,
пустые и удалённые значения остаются в самом черновике. Слова и относительные
буквенные времена всегда сохраняются полностью.

Ссылки на contours используют номер слова и порядковый номер ноты после
сортировки, соответствующей backend Save. Это сохраняет правильные данные
после удаления нот и перенумерации ID при повторной загрузке. При следующем
autosave поиск идёт по идентичности неизменяемого массива, поэтому старые ID
в восстановленном черновике не возвращают полную сериализацию.

Новый формат имеет `format: 2` и поле `changes`. Поля `document` в нём нет:
старый reader не должен принять неполные данные за самостоятельный документ.
Старые полные черновики по-прежнему читаются. Отдельно сохраняется точная форма
двухэлементных contour points: backend добавляет к ним confidence=1 при Save,
поэтому такие массивы остаются внутри черновика.

### Привязка к правильному содержимому

Номера ревизии недостаточно: удаление и импорт другого пакета могут повторно
использовать прежние song ID и revision. Перед наследованием проверяется также
`documentFingerprint`: SHA-256 прочитанного JSON-документа `lyricsSync`.
Backend вычисляет его из уже прочитанного текста; дополнительного чтения
файла нет. Save возвращает отпечаток именно опубликованного текста, совпадающий
со следующим GET. Не используется отпечаток метаданных manifest: optional
artifact checksums могли бы не заметить другое содержимое.

В renderer нет полного вычисления хеша. Проверенный промежуточный вариант
с локальным хешированием давал 35–56 мс при первом обращении и был заменён
серверным отпечатком. Во время Save также устранено повторное кодирование
документа: одни serialized bytes используются для файла, checksum и ответа.
Существующий внутренний `execute()->int` сохранён; дополнительный результат
с отпечатком используется editor API.

Старый backend без отпечатка использует прежний полный draft. При Save без
нового токена frontend явно удаляет старый токен из новой базы. Кеш проверенных
bytes держит базу через WeakRef и не удерживает большой закрытый документ
в памяти.

Несовместимая база не используется для восстановления. Исходные bytes при
чтении сохраняются. Backup для отмены preview может сохранить корректный
черновик другой ревизии/другого содержимого без попытки его реконструировать.
Это предотвращает его потерю при временном autosave и последующей отмене.

### Проверенные случаи

Регрессии воспроизводили полную сериализацию неизменившегося анализа,
повторную сериализацию после перенумерации ID, потерю чужой ревизии при отмене
и подстановку другого анализа при повторном использовании ID/revision.
Проверяются также успешный и неудачный checkpoint restore, испорченные ссылки,
границы индексов, повторные индексы, старый формат, undo/cancel, recovery dialog,
conflict/reload и дополнительные правки во время Save. Последние привязываются
к новой, только что сохранённой базе.

### Измерение окончательного варианта

Фактические `saveDraft`/`loadDraft`, документ из 2000 нот, 128 000 contour points,
10 000 activity intervals и 2000 rhythm points. 25 повторов; полная запись
и обычная компактная запись чередуются. Во всех повторах проверено точное
совпадение JSON восстановленного документа.

| Показатель | Полный draft | Компактный draft |
| --- | ---: | ---: |
| Объём данных | 3 075 745 байт | 212 751 байт |
| Медиана повторной записи | 42,236 мс | 5,642 мс |
| Медиана повторного чтения | 33,887 мс | 4,223 мс |

Объём уменьшился на **93,08%**. Для отдельно созданных новых баз медианы
компактной записи/чтения — **7,157/5,268 мс**. Первые обращения в процессе
заняли **10,267/19,446 мс**. Максимум компактной записи в этой выборке —
19,805 мс; максимумы чтения — 16,710 мс в повторной серии и 19,446 мс
при первом обращении. Поэтому результат не означает, что любая операция
всегда помещается в один кадр.

Среда: Linux, Node 24.22.3, jsdom с localStorage в памяти. Дисковая задержка
реального Windows storage и rendering frames здесь не измерены. Итоговый
diagnostic benchmark прошёл с исходным timeout 30 секунд; более ранний
прогон при сильной загрузке среды завершился timeout и не используется
как итоговое измерение.

Файлы: `frontend/src/pages/editor/editorDraft.ts`, `editorApi.ts`,
`useEditorSession.ts`, `python/backend/editor/{domain,get_document,save_document}.py`,
`python/backend/api/{song_dto,song_editor_routes}.py` и соответствующие regression tests.

## 2. Сравнение правок после восстановления

Recovery создаёт новые объекты нот. Прежний `isEditorDirty` сериализовал их
contours даже тогда, когда обе ноты ссылались на один неизменяемый массив.
Правка последней ноты заставляла перед этим сравнить весь анализ предыдущих.

Теперь при одинаковой ссылке на contour сравниваются оставшиеся поля ноты.
Различающиеся contours проходят прежнюю полную проверку. Правила сравнения ID,
неизвестных полей и нечисловых значений сохранены.

В регрессиях число чтений contour points уменьшилось с **65 536 до нуля**
для одинакового содержимого и с **64 512 до нуля** при правке последней ноты.
На отдельном синтетическом документе из 1024 нот × 256 points, примерно 11,25 МБ
JSON, медиана сравнения составила **129,095 → 2,057 мс**. Измерены девять серий
по пять сравнений, Node 24. Это стоимость одной операции, не общий FPS.

Файлы: `frontend/src/application/editor/editorModel.ts`,
`frontend/src/pages/editor/editorModel.dirty-performance.test.ts`.

## 3. Короткий опрос загрузки аудио

`waitForReady` каждые 25 мс запрашивал полный `GetDiagnostics`, включавший
состояние устройств, сети, graph, записи и packet trace. Ожиданию загрузки
нужны только PlaybackState и PlaybackLoadProgressFrames. Они уже доступны
в существующем `GetPlaybackSnapshot`, как и effective/requested sample rate.

Ожидание загрузки и `currentSampleRate` переведены на этот короткий снимок.
Частота опроса, состояния ошибки, timeout и проверка отмены сохранены.
Native-код использует один общий prefix для этих полей в обоих ответах.

Измерение actual native Release library с FakeAudioBackend, семь серий
по 5000 обращений:

| Показатель | Полная диагностика | Короткий снимок |
| --- | ---: | ---: |
| Размер ответа | 10 007 байт | 356 байт |
| Медиана обработки native-запроса | 30,4628 мкс | 2,02595 мкс |

Это стоимость формирования ответа и обработки запроса. Задержка реального
драйвера, IPC round trip и скорость загрузки файла этим замером не измерены.
Три новые регрессии сначала завершались ошибкой; затем прошли вместе
с потребителями загрузки, editor transport, seek, recovery и audio players:
**71 тест в шести файлах**.

Файлы: `frontend/src/services/audioSession.ts`,
`audioSession.loading-responsiveness.test.ts`.

## 4. Страницы каталога с одинаковыми датами

Сортировка по createdAt использовала отдельный индекс даты, но порядок
дополнительно разрешал одинаковые даты через возрастающий song ID.
SQLite сортировал большие группы одинаковых дат. При наличии cursor
OR-условие также заставляло заново просматривать уже показанные ID.

Добавлены четыре неуникальных индекса: оба направления даты с возрастающим ID,
с фильтром status и без него. Они устанавливаются идемпотентно на существующей
схеме 4. Дополнительная проверка колонок сохраняет поддержку частичных старых
схем при миграции.

Для date cursor выполняется до двух ограниченных диапазонных SELECT: сначала
оставшиеся ID в точной дате курсора, затем следующие даты, если страница ещё
не заполнена. Порядок, фильтры, cursor format и блокировка catalog revision
сохранены. Другие способы сортировки используют прежний путь.

6000 песен, две группы по 3000 одинаковых timestamps, страница 20 песен:

| Запрос | До, SQLite VM steps | После |
| --- | ---: | ---: |
| Первая страница, дата по возрастанию, все | 141 800 | 800 |
| Первая страница, дата по убыванию, все | 147 700 | 800 |
| Первая страница, ready | 28 500–29 300 | 800 |
| После 2000 песен, все | 63 300–66 300 | 800 |
| После 2000 песен, ready | 31 500 | 900 |

VM steps подсчитаны progress handler с шагом 100; это не миллисекунды UI.
Четыре индекса заняли 1 351 680 байт, около 1,29 МиБ, в этом fixture и добавляют
четыре B-tree entries на песню. Время записи в библиотеку отдельно не измерено.

Девять тестов сначала воспроизвели проблему. После добавления только индексов
четыре deep-cursor случая оставались медленными; разделение диапазонов устранило
и этот механизм. **53 различных адресных теста прошли**: 21 новый, 10 numeric
cursor, 12 literal search и 10 migration/lifecycle. Последний прогон повторил
31 затронутый тест после исправления проверки колонок старой схемы.

Ruff format/lint четырёх файлов, mypy для Windows трёх production-модулей
и их architecture checks прошли.

Файлы: `python/backend/infrastructure/orm.py`, `migrations.py`, `sql_songs.py`,
`python/tests/test_song_page_query_cost.py`.

## Границы результата

Хранилище черновиков остаётся синхронным localStorage. Уменьшены объём работы
и размер обычного autosave; различающиеся большие массивы и старые отдельно
разобранные черновики сохраняются полностью. Ручной Save по-прежнему передаёт
полный документ backend. Ускорение других catalog sort modes этим продолжением
не заявляется.

Синхронный UnloadSong пока сохраняет обязательный барьер закрытия файлов.
Windows Media Foundation может задерживаться внутри Flush/Release/MFShutdown.
Их перенос без проверки владения создаёт риск старых команд и незакрытых файлов;
такая неподтверждённая переделка в этот проход не внесена.

Живая проверка Windows UI, WASAPI/ASIO, физических микрофонов, переключения
аудиоустройств и двух участников комнаты через `start-multy.bat` в этой среде
недоступна. Обязательный room/audio gate из `AGENTS.md` остаётся незавершённым.
Автоматические проверки не заменяют этот сценарий.

Предыдущий опубликованный HEAD `1a804255` имеет полностью успешный
[GitHub Actions run 45459064719](https://github.com/Pro100Dimka/karaoke_new_version/actions/runs/45459064719):
frontend, native Windows, native Linux, Python fast, integration и release.
Это свидетельство относится к предыдущему HEAD, а не автоматически ко всем
изменениям данного продолжения.
