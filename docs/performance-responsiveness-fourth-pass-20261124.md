## 1. Основной компонент караоке: поиск нот по времени

После оптимизации рисования эффектов в предыдущем проходе в самом
`KaraokeStage.PianoRoll` оставались два независимых полных обхода песни:
проверка наличия нот в видимом окне и поиск ноты для высоты записанного
голоса. Они повторялись на каждом обновлении плавной позиции.

`RollFxNoteIndex` теперь предоставляет `firstOverlapping(start, end)`.
Метод пропускает временные блоки вне диапазона и возвращает первую
подходящую ноту в исходном порядке, без создания промежуточного массива.
Компонент создаёт индекс через `useMemo` при изменении массива нот.

Сохранены включённые границы интервалов, исходный порядок, длинные
перекрывающиеся ноты, перемешанные ноты и независимое время захвата голоса.
Смена документа или тональности создаёт новый массив и новый индекс.
Частота кадров, графические эффекты и точность высоты не сокращались.

### Измерение

Настоящий компонент, 10 000 нот, 60 обновлений позиции после первоначального
построения индекса. Счётчики измеряют обращения к свойствам нот.

| Чтения свойства | До | После |
| --- | ---: | ---: |
| `start` | 555 200 | 1 380 |
| `end` | 1 079 785 | 5 860 |
| Всего | 1 634 985 | 7 240 |

Повторные чтения сокращены на **99,56%** в этом сценарии. Это измерение
объёма работы JavaScript, не FPS и не задержки GPU. Первичное построение
индекса остаётся линейным; сильно перемешанные временные блоки могут
требовать большего обхода.

**17 адресных тестов** `KaraokeStage` и `rollFxNotes` прошли. Проверены
seek назад, zoom, время захвата, границы блоков, смена документа и
тональности, пустая песня и совпадение с прежней семантикой выбора ноты.
Регрессия сначала воспроизведена на прежней реализации.

## 2. Обновление прогресса без перечитывания всей истории задач

Подписка приложения обновляет список задач при событиях прогресса с
объединением событий за 250 мс. Раньше каждое обновление читало все
страницы `/jobs`, включая давно завершённые задачи. Большая история
повторно проходила через БД, HTTP, Electron и преобразование DTO.

Теперь события известных ID выбирают полные авторитетные ответы
`GET /jobs/{id}`. Обновлённые записи заменяют соответствующие элементы
кешированного списка, сохраняя его порядок и ссылки на остальные записи.
Событие само по себе не подменяет DTO: название, backend обработки,
ошибка, отчёт и timestamps читаются из ответа сервера.

Полный список по-прежнему читается при запуске, ручной инвалидации,
переподключении, `resync`, появлении неизвестного ID и плановом опросе.
Отдельная проверка прошедших 30 секунд обеспечивает полную сверку даже
при непрерывных событиях прогресса, которые сдвигают таймер опроса.
Полная сверка также выполняется при исчезнувшей задаче или неполном
ответе точечного чтения.

### Ограничения параллельности и защита от устаревших ответов

- Одновременно отправляется не более восьми точечных HTTP-запросов.
  Вся текущая группа завершается перед следующей группой или полным
  fallback: уже отправленную работу desktop bridge отменить нельзя.
- Отмена останавливает последующие группы, страницы и fallback,
  освобождает подписки и запрещает публикацию ответа.
- ID и revisions остаются ожидающими до принятия результата существующим
  барьером состояния. Ошибка, отмена или повторное чтение не теряют ID.
- Событие другой задачи во время чтения добавляется к следующему чтению.
  Более новое событие того же ID не подтверждается старым ответом.
- Начатая полная сверка остаётся полной при повторе после терминального
  события. Найденные новые задачи не исчезают при возврате к старому кешу.
- Проверяется полнота каждой записи и точное множество запрошенных ID.
  Ссылочный, дублированный, неожиданный или неполный результат не заменяет
  кеш частично.

## 3. История высоты голоса без постоянных аллокаций worker

Analysis worker добавлял наблюдения в `std::deque` и удалял старые элементы
при превышении 256. Даже после заполнения ограниченной истории это
регулярно выделяло и освобождало память под `pitchMutex_`, который также
нужен читателю истории.

История заменена на фиксированное кольцо `std::array` из 256 наблюдений.
Worker перезаписывает следующий элемент без аллокации. Публичный
`pitchHistory()` по-прежнему возвращает собственный `std::vector` в
хронологическом порядке: при обходе кольца копируются два последовательных
участка. Владение, mutex, generation, sequence и поля наблюдения сохранены.
Реальный аудиопроизводитель по-прежнему не берёт `pitchMutex_`.

### Измерение

Регрессия включает счётчик аллокаций только на настоящем analysis worker.
После прогрева подаются 80 блоков по 2048 отсчётов, создающих 320 следующих
перекрывающихся наблюдений и несколько переходов через границу кольца.

| Операция на worker после прогрева | До | После |
| --- | ---: | ---: |
| Выделение памяти | 35 | 0 |
| Освобождение памяти | 9 | 0 |

Это отсутствие аллокаций в проверенном пути обновления истории, а не во
всём AudioService. Возвращаемый читателю vector по-прежнему выделяет память.
Окно оценки высоты, частота анализа, качество обработки и PCM-путь не менялись.

**8 адресных native tests прошли**, включая полный порядок последних 256
записей, все поля и capture times, частичное заполнение, очистку при смене
generation, продолжение sequence, live pitch, device-sized blocks,
тихий голос, согласные и IPC lifecycle. После изменения header пересобраны
затронутые потребители.

## 4. Восстановление одной записи без обхода всей коллекции

При восстановлении известного `recording_id` backend сначала искал все
recovery descriptors во всех каталогах записей, затем отбрасывал чужие ID.
Это происходило и при восстановлении одной записи после сохранения.

`recovery_descriptors(recording_id)` теперь ищет фиксированное имя
`recording-recovery.json` только внутри проверенного каталога этой записи.
ID используется как буквальное имя каталога, поэтому допустимые имена
с символами glob, например `take[1]`, не превращаются в шаблон.
Вызов без ID сохраняет прежнюю полную сверку.

Настоящий API-сценарий с 1500 соседними каталогами выполнял **1502 вызова
`scandir`**. Теперь требуется **не более одного**, только в выбранном
каталоге. Проверены восстановление аудио, пустая запись и отсутствующий
descriptor. Семантика повреждённых descriptors, dangling symlinks,
ownership файлов, исправления WAV и регистрации не изменена.

**33 адресных backend tests прошли**: 14 новых, 4 ownership, 12 empty cleanup
и 3 сценария гонки удаления/регистрации. Ruff, formatter, scoped architecture
и mypy с импортами для трёх production-модулей прошли. В Linux-тесте
подменена только Windows-операция открытия остановленного файла; реальные
repair, регистрация и файловые проверки выполнены.

## 5. Ресурсы выполняемой обработки освобождаются до терминального статуса

При проверке CI предыдущего HEAD обнаружен сбой release job
[`138740455926`](https://github.com/Pro100Dimka/karaoke_new_version/actions/runs/45477202715/job/138740455926):
`test_original_recognition_uses_the_catalogue_language_within_the_cpu_budget[2-1-recognition]`
получал `Failed`, пока CPU/RAM/VRAM ещё числились зарезервированными.
В этом release job остальные 3741 тест прошли, 10 были пропущены.

Причина — существовавшая и в `main` гонка: менеджер записывал и публиковал
терминальное состояние, затем выполнял `StartProcessing._finish()` с
восстановлением состояния песни, освобождением владения и resource lease.
Немедленный повтор после видимого завершения мог встретить ещё занятые
ресурсы.

Исправление ограничено `StartProcessing`. Выполняемая работа обёрнута в
одноразовый `ExitStack`; финализация завершается перед возвратом результата
или передачей исключения менеджеру. Прежний `on_finally` вызывает тот же
`close()` как fallback для отмены до начала работы и admission failure.
Повторный callback не освобождает владение новой задачи.

Общий жизненный цикл других типов задач и семантика немедленной отмены
очереди не менялись. Новых блокировок нет. Небольшой helper сохраняет
архитектурный предел размера функции; проверка не ослаблялась.

### Проверки

Детерминированный тест удерживает настоящий `ResourceLease.release()`
через `Event`, без гонки на скорость. На прежней реализации три исхода
выполняемой работы — успех, ошибка и отмена — публиковали терминальное
состояние до освобождения ресурсов. После исправления статус остаётся
`Running` либо `Cancelling` до завершения cleanup.

Пять новых сценариев проверяют три исхода, отмену до входа в work,
ошибку финализации, нулевой остаток reservations, ровно одно освобождение
и сохранение нового владельца, появившегося при terminal event.

Первый связанный прогон дал 65 passed / 4 failed. Три ошибки были
10-секундными ожиданиями более ранних стадий DecodeNormalize или
ProjectValidationPublication, до изменённой финализации. Четвёртая
показала старое допущение ownership-теста: callback освобождения владения
песней принимался за завершение всей задачи, хотя resource lease ещё
освобождался. Тест теперь после этого callback ждёт реальный терминальный
статус; все проверки результата, revision и владения сохранены.

После окончательной правки **10 выбранных тестов прошли**: пять новых,
исходный упавший CI-параметр, три случая с прежним stage timeout и
ownership cancellation. Тайм-ауты и остальные пороги не увеличивались;
первоначальные ошибки и логи сохранены. Полный release suite локально
не повторялся. Ruff, formatter, полный Python architecture и mypy с
импортами для изменённого модуля прошли.
