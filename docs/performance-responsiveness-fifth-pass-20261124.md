# Отзывчивость: пятый проход 24 ноября 2026 года

Работа продолжена в ветке `perf/responsiveness-20261124` от
`d3d0f874c777beb2fd012d5656bc30a9fcb1e444`. Ветка `main` не изменялась.
Предыдущие изменения описаны в
[четвёртом отчёте](performance-responsiveness-fourth-pass-20261124.md).

Ниже приведены воспроизведённые причины лишней работы и задержек, исправления
и границы проведённых проверок. Измерения относятся к указанным сценариям;
они не являются обещанием отсутствия любых задержек на любом оборудовании.

## 1. Строки караоке: поиск по временным блокам

На каждом обновлении позиции `currentLineIndex()` просматривал предыдущие
строки песни, а компонент отдельно искал будущую строку. Эти обходы
повторялись при неизменном документе, в том числе в режимах, которым поиск
для титров не требовался.

Индекс хранит границы блоков по 128 строк и позволяет пропускать блоки,
которые не могут содержать нужный интервал. Он привязан через `WeakMap`
к неизменяемому массиву строк. Поиск будущей строки использует тот же
индекс. Сохранены исходный порядок выбора, включённые границы активного
интервала, строгое начало будущей строки, перекрытия и обратная перемотка.

Измерение в настоящем `KaraokeStage`: 1000 строк, 60 обновлений позиции
после построения индекса.

| Режим | Чтения `start` + `end` до | После |
| --- | ---: | ---: |
| Classic | 163 140 | 1 860 |
| Alternating | 163 140 | 1 860 |
| Credits | 163 500 | 2 220 |

Это уменьшение повторных обращений к данным примерно на 98,6–98,9%.
Частота кадров, качество текста и временные границы не сокращались.
Начальное построение индекса остаётся линейным; беспорядочные интервалы
могут требовать просмотра большего числа блоков.

Регрессионные проверки сначала упали на старой реализации.
**55 тестов в четырёх наборах прошли**, включая все три режима настоящего
компонента и сравнение выбора строки с исходной семантикой.

## 2. Перетаскивание нот: повторное использование справочников

Каждый preview перетаскивания заново собирал сведения обо всех словах
и соседних нотах из неизменного начального документа. Для большой песни
это происходило при каждом движении мыши.

Справочники слов и группировка нот по словам теперь кешируются по ссылкам
на неизменяемые массивы. Невыбранные соседние ноты определяются один раз
для каждого выбранного слова в текущем preview. Смена выделения,
документа или массива создаёт соответствующие новые данные. Кеши
сохраняют прежнюю обработку дублирующихся ID, порядок нот и ограничения
редактирования. Объекты и массивы результатов по-прежнему создаются там,
где они необходимы для истории и геометрии изменения.

Измерение: 8000 нот, 2000 слов, 30 preview после прогрева справочника.

| Операция и повторные чтения | До | После |
| --- | ---: | ---: |
| Move: `wordId` посторонних нот | 479 760 | 0 |
| Move: ID слов | 108 060 | 0 |
| Resize: `wordId` посторонних нот | 239 880 | 0 |
| Resize: ID слов | 54 030 | 0 |

Ноль относится к указанным лишним чтениям, а не ко всей работе preview.
Проверены отсутствие квадратичного обхода при большом выделении одного
слова, сохранение contour, смена выделения и замена массивов.
**59 тестов модели и потребителей в пяти наборах прошли.**

## 3. Длительность редактора: исключён пересчёт при движении нот

`documentEnd()` зависит от слов и длительности песни. Однако зависимость
мемоизации от всего документа заставляла заново читать все слова после
каждого изменения только нот. Зависимости уточнены до массива слов и
загруженной сессии.

На настоящей странице редактора за 20 изменяющих геометрию preview число
повторных чтений окончания удалённого слова уменьшилось с **8040 до 0**.
Обновление нот при этом проверяется отдельно и продолжает происходить.
**35 тестов жестов, времени и виртуализации прошли.** Часть этих тестов
также входит в проверки предыдущего пункта: суммарно для пунктов 1–3
прошло **133 разных теста в 11 файлах**, без двойного подсчёта запусков.

## 4. Сетевой голос: рабочие буферы используются повторно

При приёме каждого пакета создавались новые PCM-векторы для декодирования
и пересчёта частоты. Отдельные временные векторы также требовались для
retiming и concealment. Кодировщик Opus на отправке не использовал уже
выделенную ёмкость буфера пакета.

В receive worker добавлены отдельные буферы декодирования, ресемплинга
и retiming; их использование остаётся под прежним `remoteMutex`.
PCM/Opus codec принимает необязательный повторно используемый выходной
буфер. Истории декодера и concealment остаются отдельными для каждого
участника. PCM копируется в собственную очередь до повторного применения
буфера, поэтому следующий певец не может заменить уже поставленные данные.

Для 200 пакетов после прогрева:

| Операции с динамической памятью внутри проверенного приёма | До | После |
| --- | ---: | ---: |
| Выделения | 400 | 0 |
| Освобождения | 600 | 200 |

Оставшиеся освобождения относятся к входным payload пакетов. Первый пакет
и увеличение требуемой ёмкости могут по-прежнему выделять память.

Тест использует настоящий `drainRemotePackets`: PCM и Opus, 44,1/48/96 кГц,
две последовательные generation, два чередующихся участника. Проверяется
точное совпадение float-данных обоих выходных каналов, очередей и deadlines.
**11 адресных native-тестов прошли**, включая потери пакетов, восстановление,
ошибки декодирования, повторные переключения формата и фиксированный потолок
задержки. Частота пакетов, формат аудио и архитектура комнаты не менялись.

Эти проверки не заменяют обязательный живой сценарий комнаты; его статус
указан ниже.

## 5. Карточки записей: выбор последнего анализа через индекс

Список записей выбирал последний анализ через `row_number()` над всей
историей анализов видимых записей. Даже для одной страницы стоимость
запроса росла вместе с историей уже завершённых анализов.

Один SQL-запрос теперь передаёт ID запрошенных записей через `json_each`
и выбирает первую строку для каждой записи через составной индекс
`(recording_id, created_at DESC, analysis_id)`. Отдельных HTTP- или
SQL-запросов на каждую карточку нет; тяжёлые details JSON не читаются.
Миграция добавляет индекс и в существующую базу, сохраняя данные и версию
схемы. Сохранён порядок при совпадении timestamps.

Измерение работы SQLite для страницы из 200 записей:

| Число анализов в истории | Шаги VM до | После |
| --- | ---: | ---: |
| 800 | 59 600 | 9 000 |
| 20 400 | 1 274 800 | 9 000 |

В большем сценарии число шагов уменьшилось на **99,29%**. Это счётчик
работы SQL, а не измерение времени диска. **13 адресных тестов прошли**:
результаты, статусы, дубликаты входных ID, порядок, потребители,
идемпотентность миграции и rollback при ошибке создания индекса.

## 6. Закрытие окна: сохранение положения без синхронной записи

Обработчик закрытия окна синхронно записывал JSON на диск до продолжения
обычного сценария закрытия. На медленном диске это удерживало основной
поток Electron.

Границы окна фиксируются сразу, а запись выполняется асинхронно. Очередь
ограничена текущей записью и самым новым ожидающим состоянием. Штатный
выход приложения ожидает завершения принятых записей. Ошибка записи не
блокирует последующие сохранения.

При 101 вызове и удерживаемой первой записи: **101 синхронная запись
заменена на 0 синхронных и 2 асинхронные**, последняя сохраняет актуальное
положение. Повторное открытие окна до окончания записи использует последнее
принятое состояние из памяти. Это отдельно защищено тестами со старым и
усечённым JSON на диске; после завершения снова читается файл.

**11 тестов WindowState прошли.** Смежные проверки запуска MainWindow
также прошли. Гонка повторного открытия обнаружена независимым review
и исправлена до публикации ветки. Electron TypeScript проверен после
последнего изменения.

## 7. Проверка модели: отмена между блоками чтения

После скачивания проверка SHA-256 читала всю модель, даже если отмена
уже была принята. Теперь она проверяет отмену до открытия, между блоками
по 1 МиБ и после EOF. Одноаргументный контракт общего файлового hasher
сохранён; отменяемый контракт явно передаётся загрузчику моделей.

В проверке с файлом 4 194 321 байт и отменой во время первого чтения:
**вместо чтения всего файла прочитан один блок 1 048 576 байт**.
Уже начатый системный read завершается; дальнейшие блоки не читаются.

Проверены очистка временного файла и закрытие stream, сохранение ранее
установленной и выбранной модели, успешный повтор, точные SHA для пустых
и пограничных размеров. Отмена на EOF не выдаётся за успешную проверку.
**30 разных тестов прошли**, включая существующие сценарии моделей.

## 8. Анализ записи: задача появляется до чтения большого файла

Запуск анализа вычислял SHA всей записи до создания job и держал общий
lock подачи анализов. Пока POST не возвращал `jobId`, интерфейс не мог
отменить проверку; другой анализ также ожидал окончания чтения.

Теперь быстрая проверка входных данных и регистрация job выполняются
сразу. Полный отменяемый SHA — первый шаг worker перед оцениванием.
Точный digest сохраняется до scoring; пустая identity существует только
внутри незавершённой проверки и не выдаётся в DTO. Нечитаемый файл
при начальной проверке и переполнение очереди по-прежнему дают синхронную
ошибку. Ошибки самого фонового чтения завершают job и анализ с ошибкой.

Владение файлом передаётся от admission к зарегистрированной задаче без
промежутка. На время SHA сохраняется счётчик reservation, который
препятствует архивированию и удалению, но не держит lock на чтении.
После ошибки и отмены освобождаются source reservation и ресурсный lease.

Проверки показали:

- Вызовы SHA до ответа при запуске и повторе: **1 → 0**, для offline
  analysis и уже имеющегося live score.
- Для записи 4 194 316 байт отмена во время первого блока завершает
  чтение после **1 048 576 байт**, вместо обхода всей записи.
- Отмена queued job выполняется вообще без чтения аудио.
- Пока SHA одной записи удерживается тестовым барьером, повтор её запроса
  и запуск другой записи завершаются, не ожидая чтения.
- Успешный анализ и повтор после отмены получают полный правильный SHA.

**31 адресный тест прошёл**: регрессии, владение исходным файлом,
settlement, историческая валидность, API, ресурсы, dedup и live score.
Независимый review проверил отсутствие использования pending identity
в статусах, кешах и выборе результатов.

## 9. Импорт проекта: исключён лишний SHA всего архива до job

Клиент `importProject` создавал новый `Idempotency-Key` при каждом вызове.
Этот ключ нигде не сохранялся и не использовался для повторов. Транспорт
не повторяет POST автоматически; опрос состояния выполняет только GET,
а повторная попытка RoomProjectCoordinator заново вызывает клиент.
При этом backend ради одноразового ключа читал весь архив до ответа 202.

Клиент больше не создаёт этот ненужный ключ. Backend вычисляет архивный
SHA для request signature только при явно переданном непустом ключе.
Остальные ключи API сохранены. Проверки ZIP, безопасности, свободного места
и контрольных сумм извлечённых файлов выполняются в прежнем объёме.

Число полных SHA-проходов до получения job стало **1 → 0** для no-header
и empty-header. Проверка настоящего API получает job, отменяет удержанный
импорт и подтверждает отсутствие опубликованной песни.

Для явного ключа сохранены строгие правила: одинаковые байты по разным
путям возвращают ту же job; изменение байтов даже при прежних пути,
размере и `mtime`, либо изменение решения об импорте, возвращает HTTP 409.
Перекрывающиеся запросы с одним ключом создают одну задачу. Отказ preflight
не создаёт job и не резервирует ключ.

**9 backend-тестов и 37 frontend-тестов прошли**, включая клиент,
RoomProjectCoordinator, целостность пакета и сохранение ключа processSong.
Живой сценарий передачи проекта между двумя экземплярами не выполнен.

## 10. Импорт проекта: отмена внутри распаковки и проверки файлов

Наличие отменяемой job само по себе не останавливало длинные стадии:
callback не доходил до распаковки, package SHA и project SHA. Теперь оба
пути — новая ревизия и дополнение существующей — передают его в потоковое
чтение. Общий `ProjectValidator` получает hasher и checkpoint на отдельный
вызов, без изменения своего состояния и поведения редактора.

Пять регрессий с отменой после первого блока раньше дочитывали каждый
проверяемый поток до **3 145 744 байт**. После исправления распаковка и
оба SHA-прохода останавливаются после **1 048 576 байт**. Успешный импорт
по-прежнему проверяет все контрольные суммы, пути, идентичность проекта,
формат аудио и lyrics; кеш SHA для этих проверок не используется.

Новые checkpoints завершаются до начала публикации. Между публикацией
ревизии и возвратом её rollback handle нет точки отмены: внешний importer
сначала получает возможность отката. Обложка остаётся под `media_update`.

**16 тестов прошли после окончательного разделения вспомогательных методов**:
новые регрессии, cleanup, ошибки checksum, обычный импорт, supplement,
миграция, rollback и настоящий text-only save редактора через default
validator API. Повторное использование validator после отмены проверено
отдельно; отменённый callback не сохраняется в общем экземпляре.

## 11. Экспорт проекта: отмена копирования, SHA и проверки ZIP

До исправления отмена ожидала окончания снимка файлов, полного SHA всех
артефактов или заключительного `ZipFile.testzip()`. Копирование также
удерживало media lock до завершения всего большого файла.

Снимок теперь принимает checkpoint и использует переиспользуемый буфер
1 МиБ с `readinto` и `memoryview`. Вызовы без callback сохраняют прежний
путь `shutil.copyfile`/`copy2`. SHA получает тот же checkpoint. Проверка
готового ZIP читает все записи до EOF с проверкой CRC и отменой между
блоками, включая пустые записи.

Для клипа **4 194 329 байт** каждый из трёх сценариев после отмены читает
только текущий блок **1 048 576 байт**. До исправления каждый дочитывал
весь файл. Число вызовов чтения было 66 для наблюдаемого copy fallback
и 6, включая EOF, для SHA и ZIP; теперь в каждом случае 1.
Пропускная способность копирования не измерялась: это доказательство
отзывчивости отмены, а не обещание ускорить сам перенос байтов.

Отмена до `os.replace` сохраняет прежний экспорт, очищает временные
каталоги и ZIP, освобождает блокировки и не добавляет `PackageExported`.
Запоздалая отмена после успешной публикации не меняет её на `Cancelled`.
Повторный экспорт проверен с точным содержимым клипа и SHA из манифеста.

**22 разных теста прошли.** В их числе четыре отдельные проверки
повреждённого CRC первой, пустой, последней и текстовой записи: каждый
такой архив отклоняется, прежний файл остаётся на месте. Также проверены
preflight, выбор актуального клипа, snapshot при ручной замене, обложка,
compression-ratio fallback и границы отмены относительно публикации.

## 12. Архив библиотеки: отмена SHA большого файла

Экспорт и импорт всей библиотеки уже проверяли отмену между файлами,
но внутри SHA одного большого файла продолжали читать до конца.
Оба цикла теперь используют тот же отменяемый файловый hasher.
Отмена находится до сборки архива либо до восстановления библиотеки;
новых точек отмены внутри и после `restore` нет.

Для файла **4 194 321 байт** в обоих направлениях чтение сократилось
с **6 вызовов, включая EOF, до 1**, с полного файла до **1 048 576 байт**.
После принятой отмены дополнительных блоков не читается. Jobs завершаются
как `Cancelled`, handles закрываются, временный каталог очищается,
блокировки освобождаются. Исходные данные, записи и прежний архив
сохраняются; сборка нового ZIP и `restore` не запускаются.

**10 тестов прошли**: новые сценарии, существующие snapshot-проверки,
roundtrip, отказ при ошибочном checksum и rollback публикации. Отдельный
тест подтверждает, что успешное восстановление не прерывается добавленным
постфактум checkpoint. Адресный mypy с `--platform win32` также прошёл.

## 13. Дополнительный клип: отменяемая установка и откат

Дополнение уже существующей ревизии обходило транзакцию изменения медиа.
Если отмена или ошибка БД происходила сразу после установки клипа, новый
файл оставался на месте, несмотря на неуспешное завершение импорта.
Копирование самого клипа также не реагировало на отмену внутри файла.
Воспроизводящие проверки подтвердили оба дефекта до изменения production.

Теперь входящий клип копируется блоками в соседний временный файл.
Публикация проходит через уже открытую `SongMediaUpdate`, которая живёт
до завершения записи БД и `media.commit()`. Прежний клип сохраняется жёсткой
ссылкой; при отсутствии такой возможности используется отменяемое
копирование резервной копии с одним буфером 1 МиБ. Старый рабочий путь
остаётся на месте до атомарной замены, поэтому нового промежутка с
отсутствующим клипом нет.

После установки файла отмена и ошибка БД вызывают прежний механизм отката
media transaction. Если клипа раньше не было, удаляется только наш новый
файл. Проверка identity не позволяет откату затереть более новую независимую
публикацию. При невозможности восстановления резервная копия сохраняется,
а исходная ошибка не маскируется. После успешного commit временные файлы
и backup очищаются; новых проверок отмены после commit нет.

Наблюдаемая входящая копия при отмене уменьшилась с полного чтения
**3 145 731 байта до 1 048 576 байт**. На пути с жёсткой ссылкой старый
клип вообще не перечитывается. Для файловой системы без ссылок проверены
как отмена между блоками, так и полный backup с последующим восстановлением.
Это откат при отмене и ошибках исполнения; новый recovery journal для
аварийного завершения процесса не вводился.

**28 разных адресных тестов прошли**: 12 новых регрессий и 16 смежных
проверок импорта, media storage, обложек и same-revision clip. Отдельная
регрессия выявила неучтённый backup при ошибке закрытия временного файла;
его ownership теперь регистрируется до закрытия. Независимый review
окончательной реализации не обнаружил оставшихся блокирующих замечаний.

## Исправление проверки CI предыдущего прохода

В запуске `45485456484` frontend и обе native-платформы прошли, но backend
integration/release упали на тесте отмены параллельного клипа. После
исправления порядка освобождения ресурсов в предыдущем проходе тест всё
ещё ждал внутренний cleanup как будто это уже терминальное состояние job.
Между этими событиями корректно оставалось состояние `Cancelling`.

Ожидание в тесте перенесено на завершение `ProcessingJobManager._finish`.
Дополнительно проверено, что клип остановлен до освобождения ресурсов
`StartProcessing._finish`. Таймаут и прежние проверки не ослаблены,
производственный код жизненного цикла не менялся. **Оба сценария прошли**.
Это исправление воспроизведённого падения, а не утверждение, что старый
запуск CI стал успешным.

## Проверки и ограничения

Для каждого нового механизма добавлена воспроизводящая проверка и
подтверждено её падение до исправления. Проверялись затронутые потребители;
полные наборы автоматически не перезапускались. Независимые review
проверили frontend-кеши, native-буферы и жизненный цикл сохранения окна.

Проверки renderer/Electron TypeScript, архитектуры frontend/backend,
форматирования, Ruff и адресного mypy прошли. Расширенный mypy с импортами
bootstrap дополнительно обнаруживает 10 ошибок в шести неизменённых
studio-файлах. Сравнение с исходным `d3d0f87` через `--shadow-file`
подтвердило точно тот же набор диагностик; новый проход их не добавил.

Логи сохранены в рабочих каталогах:

- `frontend/artifacts/responsiveness-20261124/` — регрессии, измерения,
  TypeScript и frontend architecture.
- `.dev-data/temp/responsiveness-native/pass5/` — native build, счётчики

- `.dev-data/temp/analysis-summary/` — SQL, миграции и исходные падения CI.

Количество тестов приведено для каждой группы отдельно. Некоторые
проверки потребителей входят в несколько групп; их нельзя складывать
как число уникальных тестов всего прохода. Итоговая общая проверка
архитектуры backend прошла после объединения изменений; ограничения
на размер функций и остальные gates не ослаблялись.

**Работа, затрагивающая комнату и сетевое аудио, не прошла обязательный
живой gate и не является полностью завершённой.** В доступной Linux-среде
нет двух настоящих Windows/Electron-окон, WASAPI/ASIO и микрофонов для
запуска через `start-multy.bat`. Не выполнены взаимное пение и прослушивание,
измерение рассогласования голосов ≤30 мс, переходы воспроизведения,
проверка записи слышимого mix и переключения устройств. Также не выполнен
живой сценарий передачи проекта с сохранением loader до готовности всех
участников и доступностью управления только после readiness. Отчёт со
скриншотами и диагностикой в `artifacts/room-e2e/` отсутствует.
Автоматические проверки выше этого ограничения не снимают.
