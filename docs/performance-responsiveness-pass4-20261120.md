## Ошибка запуска со скриншота

Windows/MSVC останавливал сборку `AudioService` на `PitchEstimator.cpp`:
три внутренних объявления `lag` затеняли курсор корреляции с тем же именем.
Предупреждение C4456 превращалось в ошибку C2220, потому что проект собирается
с предупреждениями как ошибками. Это дефект предыдущей оптимизации в ветке.

Курсор переименован в `correlationLag`. Вычисления, порядок операций и
настройки компилятора сохранены. Исправление отдельно опубликовано коммитом
[`25f990cf`](https://github.com/Pro100Dimka/karaoke_new_version/commit/25f990cfef584c3714462d8d24cbc3a285d473bf).

До исправления GCC с дополнительным `-Wshadow -Werror` воспроизвёл все три
затенения; после исправления эта проверка проходит. По реальным compile
commands также проверены девять изменённых C++ translation units
(11 вариантов команд для разных targets). Новых ошибок затенения нет.
Локально собраны `AudioService` и `audioservice_tests`; прошли шесть выбранных
проверок pitch estimator и analysis engine, включая точное совпадение
результатов, повторное использование памяти и timestamps/generation.

В [GitHub Actions, run 44807306738](https://github.com/Pro100Dimka/karaoke_new_version/actions/runs/44807306738)
успешно завершились configure, build и native ctest для **Windows/MSVC**
и Linux/GCC 14 с `AUDIOSERVICE_WARNINGS_AS_ERRORS=ON`. Запуск интерфейса
и физических аудиоустройств этим не проверен.

Обновление существующей локальной ветки:

```powershell
git pull --ff-only origin perf/responsiveness-20261120
.\start.bat
```

## Караоке: расчёт оценки во время пения

### Точный кеш смешанных отклонений

Оптимизация предыдущего прохода уже ускоряла стабильное попадание в ноты.
Для смешанных отклонений внутри и снаружи допуска повторно просматривалась
вся история samples. После пяти минут следующий набор из 120 активных кадров
читал **2 095 064** старых измерения.

`performanceScoring.ts` запоминает точную сумму стабильной длительности
и границы состава вошедших samples. Пока изменение среднего не пересекает
эти границы и число samples прежнее, сумма повторно используется. При
изменении состава выполняется прежний точный проход в хронологическом
порядке. Допуск, арифметика, частота оценки и правила попадания сохранены.

### История измеренных нот без копирования на каждом кадре

`PerformanceTracker` удерживает список ссылок на уже измеренные note
accumulators. Очередной pitch frame обновляет существующий accumulator.
Список перестраивается при появлении измеренной ноты, переходе от игнорируемой
тишины к оценке, загрузке документа или сбросе.

В проверке 120 активных кадров создавали 120 массивов всей истории; теперь
создаются **четыре**, по числу новых измеренных нот. Сам score вычисляется
на всех 120 кадрах, без пропуска обновлений.

### Измерения двух изменений вместе

Сравнение с базой `1df9e6ce`: ноты по 0,48 секунды с шагом 0,5 секунды,
60 pitch frames в секунду, отклонение `2 * sin(frame * 0.13)` полутона.
После накопления истории измеряются 120 операций `update + noteScore`.
Таблица содержит медианы пяти чередующихся запусков before/after.

| Накопленная история | До, мс на операцию | После, мс на операцию | Ускорение |
| --- | ---: | ---: | ---: |
| 5 минут | 0,146912 | 0,026560 | 5,53× |
| 30 минут | 0,828850 | 0,140522 | 5,90× |
| 60 минут | 1,853344 | 0,304589 | 6,08× |

Это время указанного расчёта на тестовой машине, не общий FPS, задержка
микрофона или скорость всего приложения. Итоговые поля score во всех парах
совпали строго. Дополнительное сравнение `assert.deepStrictEqual` на
**64 fixtures и 76 800 кадрах** подтвердило совпадение score, events, hit IDs,
live target, energy и streak; включены seek, reset, transpose, contour,
confidence, игнорирование тишины и нечисловой pitch. Прошли **58 тестов
в пяти файлах**. Отдельная проверка нового теста после уточнения TypeScript
типа также прошла; она не прибавляется к этому количеству.

Остаётся проход по измеренным нотам при общей агрегации. При пересечении
границ смешанного диапазона samples нужен точный пересчёт. Таблица не
обещает постоянную стоимость для любой истории и любого характера пения.

## Редактор

### Выделение при preview большого документа

Эффект очистки выделения строил множество всех note IDs после каждого
preview, даже когда ничего не выделено. Теперь пустое выделение сразу
возвращается; при непустом проверка заканчивается после нахождения всех
выбранных IDs. Если ноты удалены, сохраняется исходный порядок оставшихся
выделенных элементов. Неизменившееся выделение сохраняет ссылку.

На 20 000 нотах и 30 preview количество лишних чтений IDs после требуемых
элементов уменьшилось **с 599 970 до нуля** для пустого выделения и для
выделенной первой ноты. В инструментированном jsdom-прогоне эти сценарии
заняли соответственно 180,13 → 25,67 мс и 127,31 → 6,97 мс.
Это время тестового потребителя, не измерение Windows layout/paint.
Проверены замена при прежнем количестве нот, удаление, offscreen selection,
undo/redo и сохранение. Пять consumer suites дали 55 успешных тестов;
отдельный offscreen deletion/undo case также прошёл.

### Резервная копия autosave и отмена preview

Перед первым отложенным autosave редактор заново разбирал сохранённый
черновик. Отмена preview затем заново сериализовала резервную копию.
Теперь checkpoint хранит исходную строку. `captureDraft` всё равно читает
storage и проверяет изменившиеся данные; повторный parse пропускается только
для уже проверенных **тех же ключа и полных байтов**. `loadDraft` по-прежнему
создаёт новый parsed object при каждом чтении. Кеш ограничен одной строкой.

На валидном черновике 3 121 260 байт, 2000 нот и 128 000 contour points
медиана трёх запусков составила:

| Операция | До | После |
| --- | ---: | ---: |
| Создание checkpoint | 15,10 мс | 0,0485 мс |
| Восстановление при отмене | 19,31 мс | 0,0811 мс |

Полный parse для неизменившейся копии: 1 → 0; полных сериализаций в цикле
«autosave + отмена»: 2 → 1. Проверены повреждённый JSON, неверная форма,
внешняя замена storage, ошибки чтения/записи, recovery, gestures, conflicts,
session lifecycle и свежие mutable documents. Совместная выборка —
**63 теста в семи файлах**, частично пересекающаяся с selection suite.

Обычная запись нового черновика всё ещё вызывает `JSON.stringify` и
`localStorage` синхронно. В этих трёх прогонах её медианы были 19,52 и
44,21 мс; ускорение самой записи не заявляется. Отдельный ручной Save через
API также сериализует весь документ; для тела 3 051 543 байта отдельный
прогон сериализации занял 38,49 мс. Это подтверждённые оставшиеся границы
больших документов, требующие отдельного решения с сохранением порядка
записи и гарантий восстановления.

## Плейлисты

Ввод названия плейлиста перерисовывал элементы управления всеми песнями.
Для 500 песен и десяти символов это давало **15 000 повторных renders кнопок**.
Поддерево списка выделено в `observer`, обработчики перемещения и удаления
стабильны. Каталог и порядок используют MobX computed, привязанные к текущим
коллекциям: сохраняется реакция на изменение observable-массивов без смены
ссылки, а также на изменение полей существующих песен.

Повторных renders кнопок при вводе имени стало **ноль**. В jsdom-сравнении
время ввода уменьшилось с 992,57 до 32,95 мс на финальном production-коде;
это инструментированный тест, а не Windows layout/paint. При review
обнаружена и до публикации исправлена регрессия
первоначального React memo: удаление/замена песни в том же observable array
оставляло устаревший каталог.

Проверены reorder/focus, удаление, порядок Save/Play, блокировка при запуске,
снятие блокировки после ошибки, замена каталога, metadata и структурные
observable изменения. **13 уникальных тестов** прошли в соответствующих
запусках; последний узкий повтор двух observable cases успешен. Ошибка
промежуточного теста songIds исправлена в fixture: обычный массив заменён
на явно observable, как требует этот сценарий.

## Electron: радио и подсветка

### Метаданные радио

ICY parser собирал аудиопрефикс через повторные `Buffer.concat`, хотя ему
нужен только короткий блок названия. При 64 KiB префикса чанками по 256 байт
он копировал **8 552 498 байт** для 48-байтовых metadata. Теперь аудиопрефикс
пропускается потоково, а metadata копируются один раз в буфер заданной
длины; максимум по ICY length byte — 4080 байт.

При 20 быстрых переключениях станций оставались 20 устаревших fetch до
15-секундного timeout. Текущий metadata poll теперь один, смена станции,
выключение и stop отменяют запрос. Generation не допускает позднюю
публикацию результата после stop. Частота опроса и путь воспроизведения
аудио сохранены. **38 тестов в пяти файлах** проверили fragmented UTF-8,
границы чанков, пустые/обрезанные/максимальные metadata, отмену и restart.

### Подсветка клавиатуры

Статичная тема и paused music больше не зависят от playback clock.
За четыре секунды/240 обновлений позиции прежние девять одинаковых apply
заменены одним; при статичной теме clock вообще не читается. Музыкальная
подсветка продолжает обновляться по прежнему расписанию и восстанавливает
актуальную позицию после resume.

В native provider уже была очередь ожидающих команд, но завершённые
одинаковые команды всё равно запускали OpenRGB. Теперь кешируются последние
успешные нормализованные аргументы. Ошибка и повторное обнаружение устройств
сбрасывают кеш, включая discovery во время незавершённой команды.
**120 последовательных одинаковых запросов → один native запуск**.
Смена цвета, яркости, отключение и повторная попытка проверены. Всего
**14 уникальных тестов** в пересекающихся hook/provider наборах.
Физическое OpenRGB-устройство здесь не подключалось.

## Комнаты: ожидание обновлений без занятых рабочих потоков

`/rooms/{id}/changes` удерживал общий AnyIO worker token до 25 секунд,
пока ожидал изменения комнаты. Настоящий frontend watcher постоянно держит
такой long poll. При заполнении пула наблюдателями независимая управляющая
операция не отвечала за 300 мс; воспроизведено для пулов из 2 и 40 tokens.

Ожидание переведено на async Future с безопасным уведомлением event loop
из другого потока. Регистрация происходит до первого чтения snapshot,
waiter удаляется при результате, timeout и cancel. Короткие SQLite-чтения
остаются в worker. Существующий синхронный consumer, cursor, membership,
25-секундный timeout и семантика удаления сохранены.

**38 выбранных Python tests** прошли, включая race регистрации/чтения,
несколько event loops, отмену при незавершённом начальном чтении, удаление
после большого cursor, snapshots, activity, cleanup и identity. Ruff/format
пяти файлов и mypy двух production файлов прошли. Architecture checker
содержит **11 прежних замечаний, новых нет**. В удалённом CI jobs `fast`
и `release` остановились на этих же 11 замечаниях; весь workflow зелёным
не объявляется. Название job `release` здесь обозначает проверку, публикации
релиза из этой рабочей ветки не было.

**Живая проверка комнат остаётся незавершённой.** Корневой `AGENTS.md`
требует `start-multy.bat`, два настоящих Windows Electron-окна, обновления
комнаты и controls, reconnect, leave/close и отсутствие оставшихся процессов.
Эта Linux-среда не предоставляет такой запуск. Автоматические tests не
заменяют этот обязательный gate. Audio deadlines, buffers, room protocol,
WASAPI Exclusive и mix-minus данным изменением не затронуты.

## Проверки и воспроизведение

Полные локальные логи этого прохода сохранены в
`/workspace/scratch/ac2609fff7b1/checks/pass4/` по областям `native`,

suites и измерения предыдущих проходов повторно не запускались.

# Из корня; каталог build должен быть заранее сконфигурирован

прошли отдельно от consumer tests. Vite предупреждает о существующем

начальной загрузки. Глобальный Python architecture gate остаётся красным
из-за указанных прежних замечаний.
